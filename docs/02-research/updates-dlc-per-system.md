# Updates, DLC, demos and revisions per system

Research for TODO 2.1 (2026-11-01). Four researchers plus one adversarial verifier per group, who opened every cited source (3dbrew, switchbrew, wiiubrew, wiibrew, psdevwiki, Dolphin, Azahar, RPCS3, Vita3K, shadPS4, Xenia and others) and corrected or dropped what did not hold. Coverly may only use plaintext metadata: every field below says whether it needs keys.

## Nintendo 3DS (CIA / .3ds / .cci / .cxi / .cfa; Azahar .zcia/.zcci)

**Formats.** CIA: installable package laid out as header, cert chain, ticket, TMD, contents, then an optional meta section (that order is VERIFIED on 3dbrew CIA, and each section is 64-byte aligned). .3ds/.cci: NCSD cart image holding NCCH partitions. .cxi: executable NCCH. .cfa: data-only NCCH (e-manual, DLP child, DLC contents, update data). Azahar's compressed .zcia/.zcci (Z3DS) is unverified here. Encrypted retail dumps and 'decrypted' dumps (NCCH flags[7] NoCrypto 0x4 set) both circulate.

**Telling base / update / DLC / demo / revision apart.** Use the u64 Title ID. The high word is CCCCABCD, where CCCC=0004 is 3DS and ABCD is a category bitmask. VERIFIED on 3dbrew Titles: Normal 0x0, DlpChild 0x1, Demo 0x2, Contents 0x3, AddOnContents 0x4, Patch 0x6, CannotExecution 0x8, System 0x10, RequireBatchUpdate 0x20, NotRequireUserApproval 0x40, NotRequireRightForMount 0x80, TWL 0x8000. Values that follow from it: 00040000 = base application, 00040002 = demo, 0004000E = update (Patch 0x6 | CannotExecution 0x8), 0004008C = DLC (0x4 | 0x8 | 0x80; 3dbrew names 0004008C as the DLC directory), 00048004 = DSiWare on 3DS, 00040001 = DlpChild, 00040010/00040030 = system apps/applets. The exact system-data high words (0004001B/0004009B/000400DB) are unverified, so ignore them for game grouping. No keys needed for the CIA metadata: the CIA header (0x2020 bytes) is plaintext; header fields: 0x00 header size, 0x08 cert chain size, 0x0C ticket size, 0x10 TMD size, 0x14 meta size, 0x18 content size (u64), 0x20 content index bitmap (0x2000 bytes). The TMD is plaintext. VERIFIED: the header starts after the signature block, which for sig type 0x00010004 (RSA-2048 SHA256) is 4 + 0x100 + 0x3C pad = 0x140 bytes; Title ID is at header +0x4C (absolute 0x18C), Title Version u16 at header +0x9C (0x1DC), Content Count u16 at +0x9E (0x1DE). Each content chunk record is 0x30 bytes: id u32 @0, index u16 @4, type u16 @6 (1 Encrypted, 2 Disc, 4 CFM, 0x4000 Optional, 0x8000 Shared), size u64 @8, SHA-256 @0x10. The content table follows the 0x40-entry info records, at TMD header +0x9C4 (absolute 0xB04 for RSA-2048); that offset is from 3dbrew memory, so verify it. Content index 0 = main CXI, 1 = manual, 2 = DLP child; DLC has many indexes. Ticket (RSA-2048, data starts at 0x140): Title ID at ticket data +0x9C (absolute 0x1DC), plaintext. The title key at +0x7F is encrypted with the common key, but Coverly never needs it. Meta section (plaintext): 0x000 dependency list (0x180 bytes, from ExHeader), 0x300 core version, 0x400 SMDH icon (0x36C0 bytes); it is absent for TWL CIAs and CIAs with no CXI, so update and DLC CIAs usually lack the icon. NCCH (no keys for the header): 3dbrew lists only ExHeader/ExeFS/RomFS as AES-CTR encrypted, so the header itself is plaintext. Fields: magic 'NCCH' 0x100, content size 0x104, partition ID 0x108, maker code 0x110, version 0x112, program ID 0x118, product code 0x150 (0x10 bytes), flags 0x188 (8 bytes). CORRECTION: flags[5] (0x18D) is NOT a bitfield as the input stated. Bits 0-1 are the Content Form Type (0 none, 1 simple content, 2 executable without RomFS, 3 executable). Bits 2-7, i.e. flags[5]>>2, are the Content Type enum (0 unspecified, 1 System Update, 2 Manual, 3 DLP Child, 4 Trial/Demo, 5 Extended System Update). flags[7] (0x18F): 0x1 FixedCryptoKey, 0x2 NoMountRomFs, 0x4 NoCrypto. CAVEAT: when a TMD content record has type bit0 (Encrypted) set, that whole content inside the CIA is AES-CBC encrypted with the title key, so the embedded NCCH header (even its magic) is unreadable without keys. In that case use only the TMD and ticket. NCSD (.3ds/.cci), VERIFIED: magic 'NCSD' at 0x100, image size 0x104, media ID 0x108 (= base title ID), partition FS types 0x110, partition table at 0x120 (8 entries of offset+length, in 0x200-byte media units), partition ID table at 0x190. Partitions: 0 = CXI game, 1 = e-manual CFA, 2 = DLP child CFA, 6 = New3DS update data, 7 = update data. Partitions 6/7 are system-update data, NOT a game patch. The game NCCH header at partition 0 is plaintext, so a cart image is always a base (high word 00040000) or a demo (00040002). A cart Rev 1 is the same title ID with a higher version.

**Finding the base title.** Updates and DLC share the 32-bit low word of the base. base = 00040000LLLLLLLL, update = 0004000ELLLLLLLL, DLC = 0004008CLLLLLLLL, so baseId = 0x0004000000000000 | (id & 0xFFFFFFFF). That follows from the VERIFIED category bitmask scheme, and it is how CIA managers and Citra/Azahar locate updates. Demos (00040002) get their own unique ID and do not map to the full game, so match them by name. DSiWare-on-3DS (00048004) is standalone. The meta and ExHeader dependency lists name system modules, not the base game, so do not use them. The 4-char game code in the NCCH product code (CTR-X-XXXX, at 0x150) is a secondary link, readable only when the NCCH header is reachable, which means not inside an encrypted CIA content. The product-code prefix letters for update/DLC (e.g. CTR-U/CTR-M) are unverified, so do not classify by them.

**Version.** TMD Title Version u16, at absolute 0x1DC for RSA-2048 TMDs (VERIFIED offset), always plaintext. The bit layout (major 6 bits = v>>10, minor 6 bits = (v>>4)&0x3F, micro 4 bits = v&0xF) is the widely used community convention; 3dbrew's TMD page gives no bit layout, so it is medium confidence. Example: v2069 = 0x815 = 2.1.5, and v1024 = 1.0.0. Updates typically step through v1024, v2048, v3072 and so on. The ticket also has a title version u16 at ticket data +0xA6. NCCH 0x112 is the NCCH format version, NOT the title version. The remaster version sits in the ExHeader, which is encrypted unless NoCrypto is set. hShop pages show the version and title ID explicitly.

**What emulators and frontends expect.** Azahar (Citra successor): load the base .3ds/.cci/.cxi/.3dsx directly, or install a base CIA. Updates and DLC must be installed with File > Install CIA. Citra/Azahar unpack them into sdmc/Nintendo 3DS/<id0>/<id1>/title/<high8>/<low8>/content/ (with .tmd and .app files), where Citra uses all-zero id0/id1. So the update lands in title/0004000e/<low>/ and DLC in title/0004008c/<low>/. The base 00040000<low> picks up the installed update automatically when launched. Keys, per the official Azahar wiki (aes-keys page): sysdata/aes_keys.txt; encrypted CIA install needs slot0x3DKeyX + common0. Community reports say mainline Azahar now accepts only decrypted games (AzaharPlus keeps encrypted support), so treat that as medium/unverified. Real hardware (FBI etc.) also installs each CIA to SD separately. Coverly should show a single game entry with child items 'Update vX' and 'DLC', marked 'install via CIA', not as separate launchable games.

**Naming conventions.** No-Intro 'Nintendo - Nintendo 3DS (Decrypted)' / '(Encrypted)' cover carts, with tags (Rev 1), (Demo), (Kiosk), (Region). No-Intro 'Nintendo - Nintendo 3DS (Digital)' categories exist for eShop content; the exact (Update)/(DLC) tag wording is unverified. Scene/hShop-style names: 'Game (Update) v1.5.cia', 'Game (DLC).cia', '[0004000E....] Game Update'. hShop category pages (Games, Updates, DLC, Virtual Console, DSiWare, Demos, Themes...) each list Title ID, version and product code, which is consistent with the ID rules above. Prefer the TMD title ID over the filename.

**Confidence.** HIGH (verified on 3dbrew this pass): category bitmask table, low-word link arithmetic, CIA header/section layout, TMD offsets (0x18C title ID, 0x1DC version for RSA-2048), content chunk record layout and type flags, ticket title ID offset, NCCH header offsets, NCSD offsets and partition roles. CORRECTED: NCCH flags[5] layout (it is a form-type field plus a content-type enum, not a bitfield); NCSD partitions 6/7 hold system update data, not game patches. MEDIUM: the title-version bit layout (community convention, not on the 3dbrew TMD page), Azahar's encrypted-ROM policy and .zcia/.zcci details, the TMD content-table absolute offset, and the No-Intro digital tag wording. DROPPED as unverified: product-code prefixes for update/DLC and the exact system-data high words. Readable WITHOUT keys: CIA header, ticket title ID, TMD, meta, NCSD header, plaintext NCCH headers. NEEDS keys: the NCCH inside encrypted CIA content, and the ExHeader/ExeFS/RomFS of encrypted NCCH.

## Nintendo DS / DSi (incl. DSiWare)

**Formats.** .nds/.srl cart dumps (.dsi for DSi-enhanced/exclusive), decrypted DSiWare apps in .nds format, encrypted DSiWare exports (.bin/.tad, which need console keys), and zip/7z wrappers.

**Telling base / update / DLC / demo / revision apart.** There are no updates or DLC on DS/DSi. The kinds to tell apart are retail, DSi-enhanced/exclusive, DSiWare, demo/kiosk and revision. Everything below is in the plaintext NDS header (GBATEK DS Cartridge Header; well known, though not re-fetched this pass because the page was too large): title 12 bytes ASCII at 0x000, gamecode 4 chars at 0x00C, maker code at 0x010, unitcode at 0x012 (0x00 NDS, 0x02 NDS+DSi, 0x03 DSi only), ROM version at 0x01E. DSi extended header: title ID u64 LE at 0x230. VERIFIED on dsibrew Title list: high word 00030004 = DSiWare, 00030005 = built-in apps, 0003000F = non-executable data, 00030015 = title management, 00030017 = System Menu. 00030000 for DSi-enhanced/exclusive carts is NOT listed on dsibrew, so treat it as unverified. VERIFIED: the low word is the gamecode as ASCII hex (e.g. KNRV = 4B4E5256). Gamecode first-letter meanings are not standardized in the sources checked, except K/H being typical for DSiWare. Use unitcode, the title ID high word and No-Intro tags rather than the letter. Demos and kiosk ROMs are separate titles (No-Intro (Demo)/(Kiosk)). Encrypted .tad/.bin exports need DSi keys, so identify them by filename only.

**Finding the base title.** Not applicable: there are no updates or DLC. A revision has the same gamecode with a higher ROM version byte at 0x01E. Regional variants share the first 3 gamecode chars; the 4th is the region (VERIFIED examples: E USA, J JPN, P EUR, U AUS, C CHN, K KOR, V EUR+AUS). DSiWare to 3DS DSiWare: 00030004LLLLLLLL corresponds to 00048004LLLLLLLL (same low word). This follows from the 3DS TWL bit 0x8000 scheme; it is medium confidence.

**Version.** ROM version byte at 0x01E (plaintext): 0 = original, n = Rev n. The DSiWare title version is in its TMD, which is only available from NAND/CDN dumps.

**What emulators and frontends expect.** melonDS/DeSmuME/NooDS/DraStic load a .nds directly, one file per game, with nothing to install. DSiWare in melonDS needs DSi mode with a NAND and BIOS/firmware, and is imported through the DSi title manager. TWiLight Menu++ on real hardware runs .nds/.dsi from SD. On 3DS, DSiWare is a CIA with high word 00048004.

**Naming conventions.** No-Intro 'Nintendo - Nintendo DS (Decrypted)/(Encrypted)', 'Nintendo - Nintendo DSi (Decrypted)', 'Nintendo - Nintendo DSi (Digital)'. Tags: (Rev 1), (Demo), (Kiosk), (DSi Enhanced), (Beta), (Proto), region. Old scene names use the 'NNNN - Game (U)' release-number form.

**Confidence.** HIGH: there are no updates or DLC; the DSiWare/system high words, gamecode-to-low-word encoding and region letters (verified on dsibrew). HIGH from well-known GBATEK (not re-fetched): NDS header offsets. CORRECTED/DROPPED: 00030000 as the cart high word (unverified) and gamecode first-letter category meanings (not standardized, so do not rely on them). Everything needed is readable WITHOUT keys from the NDS header; only encrypted DSiWare exports need keys.

## Nintendo Switch (NSP / NSZ / XCI / XCZ)

**Formats.** NSP: PFS0 container of NCAs, plus <rightsId>.tik and .cert for titlekey-encrypted content, and sometimes .cnmt.xml/.nacp.xml/icon in scene dumps. NSZ: NSP whose NCAs are compressed to .ncz, with the first 0x4000 bytes (the original, still-encrypted NCA header) stored verbatim. XCI: gamecard image with plaintext 'HEAD' at 0x100 and a root HFS0 holding update/normal/secure/logo partitions. XCZ: XCI with NCZs inside.

**Telling base / update / DLC / demo / revision apart.** The Title ID decides the kind. VERIFIED in nxdumptool include/core/title.h: patch = app + 0x800; AddOnContent base = (app & ~0xFFF) + 0x1000; DLC n = AOC base + n, with n = 1..2000 (0x7D0); Delta = app + 0xC00; DataPatch = its DLC id + 0x800. Application IDs have their low 13 bits clear. CORRECTED rule: with low = id & 0x1FFF, 0x000 = Application (base), 0x800 = Patch (update), 0xC00 = Delta, 0x1001..0x17D0 = AddOnContent (DLC), 0x1801..0x1FD0 = DataPatch (a DLC data patch, 15.0.0+). The input's rule ('bit 12 set and low bits nonzero = DLC') misclassifies DataPatch. Demos are ordinary Application IDs, so identify them by name or NACP (NACP needs keys). Authoritative source (needs keys): the CNMT in the Meta NCA. VERIFIED switchbrew: header Id u64 @0x0, Version u32 @0x8, ContentMetaType u8 @0xC (0x80 Application, 0x81 Patch, 0x82 AddOnContent, 0x83 Delta, 0x84 DataPatch), ExtendedHeaderSize u16 @0xE, ContentCount @0x10. NCA headers are AES-XTS encrypted with header_key, so the CNMT and NACP are NOT readable without keys. Readable WITHOUT keys: (1) The PFS0 file table of NSP/NSZ is plaintext. A ticket file named '<rightsId>.tik' carries a 16-byte rights ID = the title ID (8 bytes) + zero bytes + the master-key-generation byte last; as hex, the first 16 hex chars are the title ID and the last 2 are keygen (e.g. 0100ABCD12340800000000000000000A). (2) The .tik itself is plaintext. VERIFIED switchbrew: for RSA-2048 sig, ticket data starts at 0x140; rights ID at absolute 0x2A0 (16 bytes); title key block at 0x180 (encrypted, never needed); key type at 0x281. (3) '<id>.cnmt.nca' marks the meta NCA, but its content is encrypted. (4) Scene NSPs may ship a plaintext '<id>.cnmt.xml' with <Type>, <Id>, <Version>, <RequiredSystemVersion>, <PatchId>/<ApplicationId>; its presence is not guaranteed. (5) Filename tags [TitleID][vN][UPD]/[DLC]/[BASE]. Caveat: titles without titlekey crypto (some system/gamecard content) have no .tik, so fall back to the filename. XCI: the gamecard header is plaintext (HEAD at 0x100) but holds no title ID (the gamecard info is encrypted). HFS0 listings show only NCA hashes as names, so an XCI's kind and ID need keys or the filename. XCIs are normally base games, optionally with bundled update/DLC in the secure partition.

**Finding the base title.** VERIFIED (nxdumptool): from Patch, app = patch - 0x800; from DLC, app = (aoc - 0x1000) & ~0xFFF; from DataPatch, app = ((dp - 0x800) - 0x1000) & ~0xFFF; from Delta, app = delta - 0xC00. Universal shortcut: app = id & ~0x1FFF, because app IDs have their low 13 bits clear. CNMT extended headers (needs keys), VERIFIED switchbrew: Application {PatchId u64, RequiredSystemVersion u32, RequiredApplicationVersion u32}; Patch {ApplicationId, RequiredSystemVersion}; AddOnContent {ApplicationId, RequiredApplicationVersion, DataPatchId (15.0.0+)}; DataPatch {DataId, ApplicationId, RequiredApplicationVersion}. Plaintext alternatives: the cnmt.xml fields, or the arithmetic on the .tik or filename title ID.

**Version.** CNMT Version u32 at header +0x8 (VERIFIED offset; encrypted inside the NCA, plaintext in cnmt.xml). By convention base = v0 and patches step by 0x10000 (v65536, v131072...), so version>>16 is the patch number; this encoding is not documented on the switchbrew CNMT page (medium confidence). The human-readable DisplayVersion lives in the NACP of the Control NCA, which needs keys. Without keys, use the [vN] tag or cnmt.xml.

**What emulators and frontends expect.** Ryujinx/Ryubing: base NSP/XCI files go in game directories. Updates and DLC are registered per title (Manage Title Updates / Manage DLC) rather than installed to NAND; the per-title files are games/<titleId>/updates.json and dlc.json (medium). Recent Ryubing builds can autoload updates/DLC found in the configured directories (medium). yuzu family (Citron, Eden, sudachi, suyu): File > Install Files to NAND puts update and DLC NSPs into nand/user/Contents/registered. All of them need prod.keys/title.keys and firmware. On real hardware (DBI, Tinfoil...) base, update and DLC are installed separately and linked by ID. Coverly should group by app ID with children 'Update vN' and 'DLC #n', and keep DataPatch/Delta hidden or grouped under their DLC/update.

**Naming conventions.** Common scene/Tinfoil style: 'Game [0100ABCD12340000][v0].nsp', 'Game [0100ABCD12340800][v131072].nsp', 'Game - DLC [0100ABCD12341001][v0].nsp', with optional [BASE]/[UPD]/[DLC], region and [NSZ] tags. ID regex: \[(01[0-9A-Fa-f]{14})\]; version regex: \[v(\d+)\]. No-Intro Switch digital/card tag wording is unverified.

**Confidence.** HIGH (verified this pass): ID arithmetic including Delta 0xC00, DLC index range 1..2000 and DataPatch = DLC + 0x800 (nxdumptool source); ContentMetaType values 0x80-0x84 (switchbrew NCM); CNMT header and extended-header layouts (switchbrew CNMT); ticket rights ID at 0x2A0 (switchbrew Ticket). CORRECTED: the DLC classification rule, which must exclude the DataPatch range 0x1801+. MEDIUM: the version>>16 patch-number convention, Ryujinx/Ryubing JSON names and autoload behavior, and XCI gamecard-info encryption details. Readable WITHOUT keys: the PFS0 file list, .tik rights ID, cnmt.xml (when present), filenames, XCI HEAD header and HFS0 names. NEEDS keys: NCA headers, CNMT, NACP (title, DisplayVersion) and XCI gamecard info.

## Nintendo Wii U

**Formats.** 1) Loadiine / extracted ('unpacked', decrypted) folder: <Title>/code/ (app.xml, cos.xml, *.rpx/.rpl), content/, meta/ (meta.xml, iconTex.tga, bootTvTex.tga ...). Updates and DLC use the same code/content/meta layout. Cemu treats a folder as a title if it has all three of content/, meta/ and code/, or if a selected .rpx sits in code/ next to content/ and meta/ (TitleInfo::DetectFormat). Plaintext. 2) NUS/CDN (WUP) format: title.tmd + title.tik + title.cert + 000000XX.app (+ .h3). Base, update and DLC all ship this way. Cemu recognises the filename 'title.tmd'. 3) WUD: raw disc image. 4) WUX: compressed WUD. The first 8 bytes are 57 55 58 30 2E D0 99 10 ('WUX0' followed by u32 0x1099D02E stored little-endian). 5) WUA (Cemu 2.0+ Wii U Archive): a ZArchive container. It has no encryption and its data is in zstd-compressed blocks. It ends in a 0x90-byte footer whose last u32 (big-endian) is magic 0x169F52D6 and whose preceding u32 is version 0x61BF3A01. The footer holds offset/size pairs for the compressedData, offsetRecords, names, fileTree, metaDirectory and metaData sections. The names and fileTree sections are stored uncompressed. One WUA can hold several titles (base + update + DLC). 6) WUHB (Aroma homebrew bundle) and .rpx/.elf homebrew (an RPX starts 7F 45 4C 46 01 02 01 CA FE). 7) Cemu accepts .iso as a WUD alias. Batocera also lists .wup and .squashfs.

**Telling base / update / DLC / demo / revision apart.** The reliable signal is the title-ID high word, specifically its low byte (the 'type byte'). Verified against wiiubrew Title database headings and Cemu TitleId.h: 00050000 = game application (eShop and disc). 0005000E = game update. 0005000C = game DLC. 00050002 = kiosk interactive demo and eShop demo. 00050010 = system application. 0005001B = shared data. 0005000B = shared user data (FCT). 00050030 = overlay applet. 0005004E = disc update package. 00000007, 00070002 and 00070008 = vWii titles. 0005000F = homebrew: this is a Cemu enum value (HOMEBREW), not a wiiubrew category, so treat it as unofficial. wiiubrew also notes that unofficial custom titles and vWii injections reuse 00050000 and 00050002. Cemu's IsSystemTitle tests (typeByte & 0x10). Where to read the title ID, all WITHOUT keys unless noted: (a) Loadiine: meta/meta.xml <title_id> (16 hex chars) and code/app.xml <title_id>. Both are plaintext XML. Cemu parses app.xml <title_version> as hex (std::stoull base 16). Weak heuristic: DLC usually has no .rpx in code/. Updates contain only changed files. Prefer the type byte over both. (b) NUS title.tmd is signed, not encrypted, so it is readable WITHOUT keys. Offsets confirmed on wiiubrew Title_metadata: sig type 0x000, signature 0x004 (0x100 bytes), issuer 0x140 (0x40 bytes), TMD version 0x180, title ID u64 BE at 0x18C, title type u32 at 0x194, group ID u16 at 0x198, title version u16 at 0x1DC, content count u16 at 0x1DE. The title.tik title ID at 0x1DC is not explicitly confirmed on the fetched wiiubrew page (it matches the Wii ticket layout), so prefer the TMD. The ticket's title key is encrypted: ignore it. .app contents are AES-encrypted and NEED KEYS: never read them. (c) WUA: root directory entries named '<16 hex titleId>_v<decimal version>' (Cemu ParseWuaTitleFolderName: hex in either case, no leading zeros unless the value is exactly '0', max 65535), e.g. 0005000010101c00_v0 / 0005000e10101c00_v80. You can read these names WITHOUT keys and without decompression: parse the footer, then walk the uncompressed fileTree + names sections. Reading meta/meta.xml inside the archive needs zstd decompression only. (d) WUD/WUX: partitions are encrypted with the disc key, so the title ID and TMD are NOT readable without keys. Readable WITHOUT keys: bytes 0x0 = ASCII product code 'WUP-P-XXXX' (Cemu's check is 'WUP-' at 0, then CC 54 9E B9 at 0x10000, in TitleInfo.cpp DetermineCafeSystemFileType). For WUX, translate the sector through the WUX index table first. A WUD/WUX is always a disc base game. Disc-bundled updates (0005004E) are inside the encrypted area. Demo = type byte 02. Wii U has no practical disc 'Rev' concept. Revisions are update titles.

**Finding the base title.** Keep the low 32 bits and swap the type byte. Cemu MakeTitleIdWithType does exactly t &= ~(0xFF<<32); t |= type<<32. Its comment example is 00050000-11223344 -> 0005000E-11223344, and MakeBaseTitleId maps 0E back to 00. For DLC, do the same with 0C. Formula: base = (id & 0xFFFF00FFFFFFFFFF) with type byte 00, which for Cafe titles equals (id & 0xFFFFFFFF) | 0x0005000000000000. wiiubrew confirms the Mario Kart 8 base IDs 00050000-1010EB00 (JPN, WUP-P-AMKJ), -1010EC00 (USA, AMKE) and -1010ED00 (EUR, AMKP). Each region has its own low ID, so an update or DLC only matches its own region's base. Cemu notes it is unsure whether demos (02) can have updates, so do not link demos. For WUD/WUX, which have no readable title ID, fall back heuristically: compare the update/DLC meta.xml <product_code> 4-char game code + region letter with the WUD's sector-0 'WUP-P-XXXX'. That gives a match with medium confidence only. The exact product-code prefix letter used by DLC/update meta.xml was not verified.

**Version.** u16. Plaintext locations: TMD 0x1DC (BE). meta.xml <title_version> (decimal). code/app.xml <title_version> (hex, as Cemu parses it). WUA folder suffix _v<decimal>. Base is usually v0. Updates are commonly multiples of 16 (v16, v32, v48 ...), but treat that as an observation, not a rule. Higher means newer. Display 'v48'. Do not invent an x.y.z mapping.

**What emulators and frontends expect.** Cemu (also used by Batocera, RetroBat and EmuDeck): base games come from the game paths as a loadiine folder, WUD/WUX/ISO, WUA, WUHB/RPX, or NUS title.tmd. Cemu itself needs keys.txt to read WUD/WUX/NUS, which is irrelevant to Coverly. CORRECTION: 'File > Install game title, update or DLC...' opens a FOLDER picker and requires <dir>/meta/meta.xml together with code/, content/ and meta/ (MainWindow::OnInstallUpdate). It installs decrypted loadiine-style folders, not NUS title.tmd. Installed titles go to mlc01/usr/title/<high8 hex>/<low8 hex>/ (e.g. usr/title/0005000e/<lowid>, usr/title/0005000c/<lowid>). The title list scans every dir under mlc/usr/title plus sys/title/00050010 and sys/title/00050030 (TitleList.cpp). Batocera: ROMs go in /userdata/roms/wiiu. Install updates/DLC through cemu-config by picking the update/DLC meta.xml. The data lands under /userdata/saves/cemu/... and the original ROM folder is untouched. ## Nintendo Wii

**Formats.** Disc: ISO. WBFS (magic 'WBFS' at 0; u8 hd_sector_shift at 0x08; the first disc's header copy sits at hd_sector_size = 1<<shift, usually 0x200; split .wbf1/.wbf2...). WIA/RVZ (magic 'WIA\x01'/'RVZ\x01' at 0; wia_file_head_t is 0x48 bytes; wia_disc_t at 0x48 is disc_type, compression, compr_level, chunk_size, then dhead[0x80], so the first 0x80 disc-header bytes are plaintext at file offset 0x58; disc_type 1 = GC, 2 = Wii). GCZ (u32 magic 0xB10BC001, zlib). CISO ('CISO'). NKit ('NKIT' at disc offset 0x200, per Dolphin IsNKit). Digital: WAD (Dolphin accepts u32 at offset 0x02 == 0x00204973 'Is' or 0x00206962 'ib'; header 0x20 bytes: hdr size 0x00, type 0x04, cert size 0x08, ticket size 0x10, TMD size 0x14, data size 0x18, footer size 0x1C; each section 0x40-aligned). Also extracted NAND folders (title/<high>/<low>/content/*.app + title.tmd), SD DLC content.bin (encrypted with the SD key) and homebrew .dol/.elf (apps/<name>/boot.dol + meta.xml).

**Telling base / update / DLC / demo / revision apart.** DISC header, plaintext, readable WITHOUT keys (Dolphin Volume.cpp/VolumeDisc.cpp): 0x000 = 6-char game ID. 0x006 = disc number (GetDiscNumber). 0x007 = revision (GetRevision). 0x018 = Wii magic 0x5D1C9EA3 (Dolphin checks 0x18 for Wii and 0x1C for GC). 0x020 = internal name. In WBFS add hd_sector_size. In RVZ/WIA read dhead at 0x58. In GCZ decompress block 0. The update partition on Wii discs is a System Menu/IOS update, not a game update: ignore it. Wii discs have no separate game-update titles. Fixes ship as disc revisions. WAD: the header, cert chain, ticket and TMD are plaintext, readable WITHOUT keys (only the title key inside the ticket is encrypted). TMD title ID u64 at TMD+0x18C, title version u16 at TMD+0x1DC. TMD offset = 0x40 + align64(certSize) + align64(ticketSize), matching Dolphin VolumeWad.cpp. Ticket title ID at ticket+0x1DC. Content .app data is AES-encrypted and NEEDS KEYS: do not read it. CORRECTION: when the optional WAD footer is present, it carries content 0's IMET banner header in plaintext. Dolphin reads the channel names from footerOffset + 0x9C WITHOUT keys (VolumeWAD::GetLongNames), where footerOffset = dataOffset + align64(dataSize). Title-ID high word (wiibrew): 00000001 essential system, 00010000 disc-based games, 00010001 downloadable channels, 00010002 system channels, 00010004 game channels and games that use them, 00010005 downloadable game content (DLC), 00010008 hidden channels. The low word is the 4-char ASCII code. The 00010001 first letter, per wiibrew headings: W WiiWare, F NES, J SNES, N N64, L Master System, M Genesis, E VC Arcade and Neo Geo, P TurboGrafx-16, Q TurboGrafx-CD, C C64, X both MSX and WiiWare demos (ambiguous), H channels. Demos have no flag beyond the X prefix and names/tags.

**Finding the base title.** DLC (00010005): the low ID is the base's 4-char code with the first letter lowercased, region letter kept. Examples from wiibrew: WF4x -> wF4x (0x774634xx), DJ Hero sWAx (0x735741xx), Beatles Rock Band r9Jx (0x72394Axx), Phoenix Wright WGSx -> wGSx. The base code is toupper(low[0]) + low[1..3]. Match it to the first 4 chars of a disc game ID or to a 00010001 title with the same code. CORRECTION: the claimed exceptions do not hold. wiibrew's 'sc7x' label is a typo, since its hex 734337xx decodes to 'sC7x', which follows the rule (Call of Duty: Black Ops disc SC7x). 'wM4x' is listed with a concrete region byte (774D3450 = 'wM4P'), which also follows the rule. A case-insensitive fallback is still harmless. Game channels (00010004) share the disc's 4-char code. Disc revisions share the 6-char ID and differ in byte 0x007. WiiWare/VC titles have no separate update titles, only higher TMD versions of the same ID.

**Version.** Disc: byte 0x007, plaintext. Display 'Rev N'; 0 means no tag. WAD/NAND: TMD u16 at TMD+0x1DC (BE), plaintext. Display the raw 'vN'. Two WADs with the same title ID are the same title in different versions (newer replaces older), not a base+update pair.

**What emulators and frontends expect.** Dolphin: disc images (ISO/WBFS/RVZ/WIA/GCZ/CISO/NKit) are booted from game-list folders. WADs are installed to the emulated NAND via Tools > Install WAD or right-click Install to NAND, landing in User/Wii/title/<high8>/<low8>/ (content + TMD) with tickets in User/Wii/ticket/. DLC WADs must be installed to NAND. Some games read SD DLC (private/wii/data/<id>/content.bin) from Dolphin's virtual SD. Real hardware: USB loaders use USB:/wbfs/<Name> [<GAMEID>]/<GAMEID>.wbfs (+.wbf1...). WADs and DLC are installed to NAND with WAD managers. Coverly: group by the 4-char code. The disc game or WiiWare base is the parent, 00010005 WADs are DLC, 00010004 are game channels, and different 0x007 values are revisions.

**Naming conventions.** Redump 'Nintendo - Wii': '<Name> (<Region>) (<Languages>)' with '(Rev 1)', '(Rev 2)', '(Disc 1)', '(Demo)', '(Kiosk)', '(Beta)', '(Proto)'. USB-loader style: 'Name [GAMEID]', e.g. 'Super Mario Galaxy [RMGE01]'. NUS/scene WADs: often '<high>-<low>-v<ver>.wad' or 'Name (Region) (WiiWare) (vN)'. GameTDB 6-char IDs are the cover key. No-Intro 'Nintendo - Wii (Digital)' tag spellings were not verified.

**Confidence.** High, verified in Dolphin source/wiibrew: disc header offsets and the 0x18/0x1C magics, the RVZ/WIA dhead at 0x58, the NKit marker at 0x200, the WAD header/alignment and accepted magics, the footer names readable without keys (correction), the high-word meanings, the VC prefixes (with X and E ambiguous), and the DLC lowercase-first-letter rule (the 'exceptions' were refuted). Medium: the ticket title ID at 0x1DC (standard, not re-fetched) and the WBFS header at 0x200 (it actually depends on hd_sector_shift). Low: No-Intro digital tag spellings.

## Nintendo GameCube

**Formats.** ISO/GCM. RVZ/WIA (dhead at file offset 0x58, disc_type 1). GCZ (0xB10BC001). CISO ('CISO' at 0; the data area follows the 0x8000-byte header/map). NKit ('NKIT' at 0x200; often named *.nkit.iso / *.nkit.gcz). TGC (first bytes AE 0F 38 A2; Dolphin's constant 0xA2380FAE is read little-endian). DOL/ELF. CHD in some frontends. Multi-disc games are separate images, sometimes tied together with an .m3u.

**Telling base / update / DLC / demo / revision apart.** No digital updates or DLC exist. The only kinds are base, disc number, revision and demo/promo. The disc header is plaintext (GC discs are unencrypted), readable WITHOUT keys: 0x000 = 6-char game ID (4-char code + 2-char maker), 0x006 = disc number (0 = Disc 1), 0x007 = revision, 0x01C = GC magic 0xC2339F3D (Dolphin checks 0x1C for GC and 0x18 for Wii), 0x020 = internal name (Dolphin reads 0x60 bytes; YAGCD defines the field as 0x3E0 bytes). The 4th char of the code is the region. First-letter heuristic: G = normal game, D = demo/kiosk/promo, P = special/promo discs. This is a heuristic only; confirm with Redump '(Demo)'/'(Kiosk)' tags. Triforce images keep their title in boot.id, a Dolphin special case. Where to read the header: RVZ/WIA at 0x58, GCZ by decompressing block 0, TGC after its header (at the offset the TGC header gives), CISO in the data area. opening.bnr (BNR1/BNR2) in the FST is plaintext and gives localized names.

**Finding the base title.** Multi-disc: same 6-char ID, byte 0x006 differs. Revisions: same ID, byte 0x007 differs. Regions: the 4th char differs. Group by game ID + revision and order by disc number. No update/DLC linkage.

**Version.** Byte 0x007 (plaintext). Display 'Rev N' (0 = none). Disc number at 0x006, zero-based.

**What emulators and frontends expect.** Dolphin: images in game-list folders boot directly. No NAND, no install. Discs change via Emulation > Change Disc, or automatically when the game asks for the other disc, using an .m3u playlist. Frontends (RetroArch, Batocera, ES-DE) use .m3u playlists, and ES-DE can show only the .m3u. Nintendont: games/<Name> [GAMEID]/game.iso + disc2.iso. Coverly: one entry per game ID with discs 1..N, and revisions as variants.

**Naming conventions.** Redump 'Nintendo - GameCube': '<Name> (<Region>) (<Languages>) (Disc 1)', '(Rev 1)'/'(Rev 2)', '(Demo)', '(Kiosk)', '(Beta)', '(Proto)'. Nintendont 'games/<Name> [GAMEID]/game.iso' + 'disc2.iso'. GameTDB 6-char IDs (e.g. GALE01) are the cover key.

**Confidence.** High, verified in Dolphin source: the header offsets for game ID, disc number (0x006), revision (0x007), the 0x1C magic and the name at 0x20, the GCZ/CISO/NKit/TGC magics (TGC byte order clarified), the RVZ dhead at 0x58, and the absence of updates/DLC. Medium: the D/P first-letter demo/promo heuristic, the CISO data-start offset, and the details of Dolphin's .m3u support.

## Sony PlayStation 3

**Formats.** Disc dumps: JB folders (PS3_DISC.SFB + PS3_GAME/PARAM.SFO + USRDIR) or .iso. PSN games, updates, DLC, themes and avatars come as .pkg (magic 7F 50 4B 47 '\x7FPKG'; u16 BE at +0x04 = release type 0x8000 retail / 0x0000 debug; u16 BE at +0x06 = platform, 0x0001 PS3, 0x0002 PSP/Vita). Content installed to the HDD sits in dev_hdd0/game/<INSTALL_DIR>/ with its own plaintext PARAM.SFO. .rap/.edat licences are out of scope.

**Telling base / update / DLC / demo / revision apart.** PKG, all readable WITHOUT keys (header and metadata are plaintext; verified in RPCS3 unpkg.h/unpkg.cpp). Header, big-endian: +0x08 u32 metadata offset (usually 0xC0 on PS3), +0x0C u32 metadata count, +0x10 u32 metadata size, +0x14 u32 file count, +0x18 u64 pkg size, +0x20 u64 encrypted data offset, +0x28 u64 data size, +0x30 char[48] Content ID (36 chars, e.g. EP1001-BLES01684_00-BORDERLANDSPATCH). The metadata block is a list of {u32 id, u32 size, data[size]} records. id 0x1 = DRM type. id 0x2 = content type: 0x04 GameData (RPCS3 comment: 'also patches', so it covers BOTH patches and DLC), 0x05 GameExec, 0x06 PS1 emu, 0x07 'PSP & PCEngine', 0x09 theme, 0x0A widget, 0x0B licence, 0x0C VSH module, 0x0D PSN avatar, 0x0E PSPgo, 0x0F minis, 0x10 NeoGeo, 0x11 VMC, 0x12 PS2 classic, 0x14 PSP remastered. id 0x3 = package flags: 0x10 PKG_FLAG_PATCH marks an update, 0x04 REQUIRE_LICENSE, 0x80 EDAT, 0x800 DISC_BOUND. id 0x6 = 12-byte title ID. id 0xA = install dir: a string that starts after 8 bytes of padding (RPCS3 comments it 'actual installation directory (DLC)'). The PKG's own PARAM.SFO is in the ENCRYPTED data area: RPCS3 decrypts it in read_param_sfo(). Coverly therefore classifies PKGs from header and metadata only. Folders and JB dumps have a plaintext PARAM.SFO (magic 00 50 53 46 '\0PSF'). CATEGORY codes, from RPCS3 rpcs3qt/category.h: DG disc game, HG HDD/PSN game, GD PS3 game data (patch OR DLC), 1P PS1 classic, 2P PS2 classic, 2G PS2 installed, 2D PS2 data, PP PSP game, MN PSP minis, PE PSP remaster, SD PS3 save, MS PSP save, plus apps and video (AM AP AS AT AV BV WT HM CB SF). This corrects the earlier claim that MN covers 'minis/PSP remaster'. To tell a patch from DLC: a patch has the PATCH flag (metadata 0x3, plaintext) and an APP_VER in its SFO. DLC lacks the PATCH flag and often installs only .edat files. Demo: no category or flag. Use the NoPayStation PS3_DEMOS list, or 'DEMO'/'TRIAL' in the title or content-ID label (heuristic). Disc revision: the VERSION field in the disc PARAM.SFO and in PS3_DISC.SFB (plaintext).

**Finding the base title.** By default RPCS3 installs into the 9 bytes at header offset 55 (0x37), which are chars 7..15 of the content ID, i.e. the TITLE_ID (plaintext). Metadata 0xA, when present, overrides it and gives the real install directory. Prefer 0xA over the title ID from the content ID, because DLC can use a different, PSN-style ID. Content ID layout: [region+publisher 6]-[TITLE_ID 9]_[00]-[16-char label]. A disc game's updates use the disc serial (e.g. BLES01684), so they land in dev_hdd0/game/BLES01684/. Regional SKUs have different serials, so linking across regions needs fuzzy title matching. RPCS3 links a GD update to its base by comparing the SFO TITLE_ID with dev_hdd0/game/<TITLE_ID>/PARAM.SFO.

**Version.** PKG, no keys needed: metadata 0x8 'software revision' = 1 unknown byte, 3 bytes firmware version, 2 bytes version, 2 bytes app_version (hex/BCD, e.g. 01 08 -> 01.08). Metadata 0x5 'package revision' = 2 bytes make_package_npdrm version + 2 bytes version. Folder PARAM.SFO, plaintext: APP_VER 'NN.NN', VERSION 'NN.NN', TARGET_APP_VER, PS3_SYSTEM_VER. The CDN filename tags -A####-V#### mirror APP_VER/VERSION.

**What emulators and frontends expect.** RPCS3: disc games are JB folders or ISOs added to the game list. File > Install Packages extracts a PKG to dev_hdd0/game/<install dir>/, and HG games, GD updates and DLC all end up there (updates merge into the disc-serial folder). check_target_app_version() applies only when CATEGORY == GD, TITLE_ID is set and APP_VER is set. If the package has no TARGET_APP_VER and no PATCH flag, it is treated as DLC and allowed even with a lower APP_VER. If it has no TARGET_APP_VER but has the PATCH flag, it needs APP_VER >= the installed APP_VER. If it has a TARGET_APP_VER, that must equal the installed APP_VER. Licences: .rap files in dev_hdd0/home/00000001/exdata (out of scope). Real console with multiMAN/webMAN: the same dev_hdd0/game/<ID> tree, with disc backups as JB folders in /dev_hdd0/GAMES/ or as ISOs in /dev_hdd0/PS3ISO/ (community convention, not verified in source).

**Naming conventions.** Redump PS3: 'Title (Region) (Languages)' plus '(Rev N)' / '(Disc N)'. Sony CDN patch filenames, confirmed in NoPayStation rows: '<CONTENT_ID>-A0108-V0100-PE.pkg' (A = APP_VER 01.08, V = package VERSION). DLC on the zeus CDN: '<CONTENT_ID>_bg_1_<sha1>.pkg' (not a bare '<CONTENT_ID>.pkg'). NoPayStation TSVs that exist (HTTP 200): PS3_GAMES, PS3_DLCS, PS3_DEMOS, PS3_THEMES, PS3_AVATARS, PS3_UPDATES. Columns: Title ID, Region, Name, PKG direct link, RAP, Content ID, Last Modification Date, Download .RAP file, File Size, SHA256. Scene/user names such as '[BLUS30001] (Update 1.02)' or '[DLC]' are informal. Exact No-Intro PSN set names were not verified.

**Confidence.** High: the PKG header and metadata offsets, content types, flags, install-dir logic and patch rules (read directly in the RPCS3 source), the category list (RPCS3 category.h) and the NoPayStation list names and filename patterns (fetched). psdevwiki returned 403, so nothing relies on it alone. Low: demo detection.

**Version.** PARAM.SFO (plaintext in the PKG metadata SFO and in folders/VPKs): APP_VER 'NN.NN' (Vita3K strips one leading '0'; for a patch it is the post-patch version), VERSION, PSP2_SYSTEM_VER / PSP2_DISP_VER. The sfo_info metadata record also carries psp2_system_ver (BCD). The PKG filename tags -A####-V#### mirror APP_VER/VERSION.

**What emulators and frontends expect.** Vita3K: <pref>/ux0/app/<TITLE_ID>/ for the base (an existing folder is replaced and the title gets ' (App)'), ux0/patch/<TITLE_ID>/ for updates (' (Update)'), ux0/addcont/<TITLE_ID>/<content_id.substr(20)>/ for DLC (' (DLC)'), and ux0/theme/<content_id>/ for themes. Installing a .pkg needs a zRIF or work.bin (out of scope). Installing a .zip/.vpk or copying a decrypted folder works without keys. Real console (NoNpDrm, RePatch): the same ux0:app / ux0:patch / ux0:addcont tree, and RePatch also uses ux0:rePatch.

**Naming conventions.** NoPayStation TSVs that exist (HTTP 200): PSV_GAMES, PSV_DLCS, PSV_UPDATES, PSV_DEMOS, PSV_THEMES. PSV_UPDATES columns: Title ID, Region, Name, Update Version, Required FW VERSION, PKG direct link, date, size, SHA256. PSV_DLCS adds zRIF and Content ID. Sony patch filename, confirmed: '<CONTENT_ID>-A0101-V0101-<sha1>-PE.pkg'. A DLC label typically contains 'ADDCONT' (e.g. MNRV0ADDCONTSE00), but that is a heuristic only. Community names such as '[PCSE00000] [v1.05] (Update)' are informal. Exact No-Intro PSN set names were not verified.

**Confidence.** High: content types, the plaintext SFO via metadata 14, gd/gp/ac classification, the ux0 layout, the substr(20) label and the INSTALL_DIR_ADDCONT correction (all read directly in the Vita3K and RPCS3 source), plus the NPS lists and filename pattern (fetched). Medium: the meaning of the other CATEGORY codes. Low: demo detection.

## Sony PSP

**Formats.** UMD dumps .iso and compressed .cso/.zso (also .dax/.jso). EBOOT.PBP for PSN games and homebrew. Updates as PBOOT.PBP. PSN .pkg ('\x7FPKG', platform 0x0002, '\x7Fext' at +0xC0, metadata at 0x280). DLC as EDAT/PGD files under PSP/GAME/<ID>/.

**Telling base / update / DLC / demo / revision apart.** ISO/CSO, no keys (CSO blocks are just zlib/LZ4): UMD_DATA.BIN holds a plaintext line like 'ULJM-05681|...' with the dashed disc ID and version, and PSP_GAME/PARAM.SFO is plaintext. PBP: magic 00 50 42 50 '\0PBP'. Its PARAM.SFO section is plaintext and only DATA.PSP is encrypted (PPSSPP PkgUnpack.cpp: 'only its DATA.PSP is encrypted'). CATEGORY: PG = the SFO inside an update PBOOT.PBP. PP = the outer SFO of an update .pkg ('game patch'). ME = PS1 classic (PPSSPP checks this value). UG (UMD game), EG (PSN game), MG (memory stick game) and MS (save) are standard values but were only checked in secondary sources. Note that on PS3 'PP' means a PSP game, so the code depends on the platform. Update folder: PSP/GAME/<DISC_ID>/PBOOT.PBP plus replaced data. Note: PPSSPP treats a folder with a PARAM.SFO and no EBOOT.PBP as SAVE DATA, which is why the outer SFO of an update is not installed. DLC: EDAT/PGD files (\0PSPEDAT, NPD\0 magics) with no bootable EBOOT. This is heuristic. PSN PKG: the header (Content ID at +0x30) and the metadata are plaintext (id 2 content type = 7 for PSP; id 6 title ID). Correction: PPSSPP says the metadata SFO pointer (id 14) is EMPTY for PSP packages. The PARAM.SFO and the item table are inside the AES-CTR area, so reading them needs decryption, which is out of scope. So classify PSP PKGs WITHOUT keys from: the content type, the content-ID label, and the NoPayStation PSP_UPDATES / PSP_DLCS / PSP_DEMOS lists matched on content ID. The label is unreliable: an LBP update's label is 'LBPPDLCSONYPA002', while others use '...PATCH...' or '...UPDATE...'. Content-type values 0x0E/0x0F/0x10 conflict between sources: RPCS3 says 0x0E PSPgo, 0x0F minis, 0x10 NeoGeo, and 0x07 'PSP & PCEngine'; PPSSPP's notes say 0x0E/0x0F/0x10 = PC Engine/Minis/NeoGeo. Demo: no flag; use PSP_DEMOS or the title. Revision: DISC_VERSION in PARAM.SFO and UMD_DATA.BIN.

**Finding the base title.** DISC_ID in PARAM.SFO is written WITHOUT a dash (e.g. ULJM05681); UMD_DATA.BIN and printed serials use the dashed form (ULJM-05681). An update's PG SFO (inside PBOOT.PBP, plaintext once extracted) carries the base DISC_ID and DISC_VERSION. PPSSPP ignores an update whose DISC_ID does not match the disc, and only warns when DISC_VERSION differs. The content ID's chars 7..15 = the DISC_ID. DLC folders are normally named after the base DISC_ID.

**Version.** Plaintext in ISO/CSO/PBP: DISC_VERSION 'N.NN' (disc revision), APP_VER (patch version, in the PG SFO), PSP_SYSTEM_VER (required firmware; PPSSPP saw 6.10-6.60 in updates). The outer PP SFO's VERSION is the package version, not the patch version, and it is encrypted inside the PKG. UMD_DATA.BIN also carries a version.

**What emulators and frontends expect.** PPSSPP: the base ISO/CSO/PBP can sit anywhere in the games folder. Updates go in memstick/PSP/GAME/<DISC_ID>/PBOOT.PBP plus data. PPSSPP installs update .pkg files itself (InstallPkgScreen, GameManager::InstallPkgOnThread): it strips the USRDIR/CONTENT/ prefix and does NOT install the root PARAM.SFO, PS3LOGO.DAT or icons. At boot, FindGameUpdatePBOOT() loads ms0:/PSP/GAME/<DISC_ID>/PBOOT.PBP instead of the disc EBOOT and keeps the disc mounted. DLC goes in the same PSP/GAME/<DISC_ID>/ folder as EDAT files. A real PSP uses the same ms0:/PSP/GAME/<DISC_ID>/ layout.

**Naming conventions.** Redump PSP: 'Title (Region) (Languages) (vX.YY)' or '(Rev N)'. NoPayStation TSVs that exist (HTTP 200): PSP_GAMES, PSP_DLCS, PSP_UPDATES, PSP_DEMOS, PSP_THEMES. In PSP_UPDATES the Name column often says '(Content Update v.2.05)'. Patch filenames on the tppkg CDN follow '<CONTENT_ID>-A0300-V0100-PE.pkg'. Older zeus CDN links use opaque hashed names, so the filename alone is not reliable. Content-ID labels sometimes contain 'UPDATE' or 'PATCH' (e.g. JP0177-ULJM05681_00-PJD2UPDATEVR0101).

**Confidence.** High: PG/PP, the PBOOT.PBP layout and boot rule, the DISC_ID match, the encrypted SFO and empty metadata 14 for PSP PKGs, and the PBP SFO being plaintext (all from PPSSPP docs and source). Medium: UG/EG/MG/MS (psdevwiki returned 403; not seen in source). Low-medium: DLC identification and PKG label heuristics. Content types 0x0E-0x10 conflict between RPCS3 and PPSSPP.

## Sony PlayStation 4

**Formats.** PKG (magic 7F 43 4E 54 '\x7FCNT', big-endian header), fake PKGs (fpkg), and extracted folders CUSAxxxxx/ with sce_sys/param.sfo and eboot.bin, plus sibling overlays CUSAxxxxx-UPDATE, CUSAxxxxx-patch and CUSAxxxxx-mods, and DLC folders or .zar archives under addcont.

**Telling base / update / DLC / demo / revision apart.** PKG header, plaintext (LibOrbisPkg PkgReader.ReadHeader): +0x04 PKG flags, +0x10 u32 entry_count, +0x14 u16 sc_entry_count, +0x18 u32 entry_table_offset, +0x20 u64 body offset, +0x40 Content ID (36 chars), +0x70 DRM type (0xF = PS4), +0x74 u32 content type (0x1A GD = app, patch or remaster; 0x1B AC = DLC with data; 0x1C AL = licence-only DLC; 0x1E DP = delta patch), +0x78 u32 content flags (0x00100000 FIRST_PATCH, 0x00200000 PATCHGO, 0x00400000 REMASTER, 0x00800000 PS_CLOUD, 0x02000000 GD_AC, 0x04000000 NON_GAME, 0x40000000 SUBSEQUENT_PATCH, 0x41000000 DELTA_PATCH, 0x60000000 CUMULATIVE_PATCH). Entry table: entry id 0x1000 PARAM_SFO. LibOrbisPkg reads it at entry.DataOffset with NO decryption, so it is plaintext without keys (unlike LICENSE_DAT, which it decrypts). Entries 0x1200 ICON0_PNG and 0x1220 PIC0_PNG are also in the table and are generally plaintext, but that was not verified in the reader code. The PFS image is encrypted and not needed. PARAM.SFO CATEGORY (LibOrbisPkg ParamSfo.cs): ac Additional Content, gc Game Content(?), gd Game Digital Application, gda System App, gdc Non-Game Big App, gdd BG App, gde Non-Game Mini App/Video Service Native App, gdk Video Service Web App, gdl PS Cloud Beta App, gdO PS2 Classic, gp Game Application Patch, gpc/gpd/gpe/gpk/gpl (the matching patches), sd Save Data. APP_TYPE (integer SFO key): 1 PAID_STANDALONE_FULL, 2 UPGRADABLE, 3 DEMO, 4 FREEMIUM, so APP_TYPE = 3 means a demo (plaintext). Folders: read sce_sys/param.sfo directly. A -UPDATE or -patch suffix marks an update overlay.

**Finding the base title.** TITLE_ID CUSAxxxxx (other prefixes also exist) is shared by an SKU's base, patch and DLC. Content ID: [region+publisher 6]-[TITLE_ID 9]_00-[16-char label]. shadPS4 takes the entitlement label as CONTENT_ID.substr(20) (ORBIS_APP_CONTENT_ENTITLEMENT_LABEL_OFFSET = 20) and accepts a DLC only if its SFO CATEGORY starts with 'ac'. Cross-SKU DLC: the base SFO keys SERVICE_ID_ADDCONT_ADD_1..7 hold service IDs like 'UP0000-CUSA00000_00'. shadPS4 also scans addcont/<service_id.substr(7,9)>/ for each one, and service label 0 = the base CONTENT_ID up to its last '-'.

**Version.** PARAM.SFO (plaintext in the PKG entry table and in folders): APP_VER 'NN.NN' (the post-patch version for a patch), VERSION 'NN.NN' (master version), SYSTEM_VER (u32). A CUMULATIVE patch replaces earlier ones; a DELTA patch (content type 0x1E or flag 0x41000000) needs the previous version. The PKG header also has version_date at +0x80 and version_hash at +0x84.

**What emulators and frontends expect.** shadPS4: the base is an extracted folder <games>/CUSA12345/. Overlays are probed in order: '-mods' first, then '-UPDATE', and '-patch' only if there is no -UPDATE folder (fs.cpp). Patches can be disabled (ignore_game_patches). DLC: <addon_install_dir>/<TITLE_ID>/<any subfolder or .zar>/sce_sys/param.sfo. The default addon_install_dir is <user dir>/addcont. The subfolder name is NOT required to be the label, because shadPS4 reads CONTENT_ID from each SFO. DLCs are mounted as /addcont<N>. Licences come from <licenses dir>/<service_id>.idx/.rif (out of scope). shadPS4 main no longer contains a PKG installer (src/core/file_format/pkg.cpp is gone), so PKGs must be extracted externally. Real console/GoldHEN: /user/app/CUSA..., /user/patch/CUSA..., /user/addcont/CUSA.../<label> (community knowledge, not verified in source).

**Naming conventions.** Sony CDN/fpkg style: '<CONTENT_ID>-A0105-V0100.pkg' (A = APP_VER, V = VERSION), carried over from PS3/Vita where it is confirmed; for PS4 this was not verified against a primary source. DLC packages are usually named by content ID. Scene names such as 'Title [CUSA12345] [v1.05] [Update]', '(DLC)' or 'CUSA12345-patch' are informal. Redump covers PS4 discs; claims about No-Intro PS4 DATs were not verified.

**Confidence.** High: the header offsets, including the now-verified entry_count/entry_table_offset; content types and flags; the plaintext PARAM_SFO entry; the SFO category list and APP_TYPE; the shadPS4 overlay order, addcont layout, substr(20) and SERVICE_ID_ADDCONT_ADD linking (all read in source). Medium: PS4 filename conventions and real-console paths.

## Sony PlayStation 5

**Formats.** PKG with outer magic 7F 46 49 48 '\x7FFIH'. The embedded '\x7FCNT' header's offset is a LITTLE-endian u64 at FIH+0x58, and the CNT header itself is big-endian, 0x5A0 bytes. A standalone \x7FCNT envelope also exists, and PkgToolBox tells it apart from PS4 by looking for param.json. Decrypted folders PPSAxxxxx/ with sce_sys/param.json (JSON, not SFO), .ffpkg/.ffpfs images, and sibling update or DLC folders. PS4 (CUSA) titles on PS5 follow the PS4 rules.

**Telling base / update / DLC / demo / revision apart.** Folders, readable WITHOUT keys: sce_sys/param.json. A patch has originContentVersion and targetContentVersion (e.g. 01.000.000 -> 01.043.000) and usually versionFileUri. A base has no origin or target fields. 'addcont' in param.json is an object holding serviceIdForSharing (the SKU IDs whose DLC the app accepts); it does NOT mark the package as DLC. DLC is recognised heuristically: it sits under addcont/<PPSA>/<label>/, its content-ID label differs from the base's, and it has no eboot.bin. PKG: CNT+0x40 content ID and CNT+0x74 content type are plaintext, using the PS4 scheme (RPCS3 lists 0x20 as PS5 GameData). The param.json entry in a PKG may be encrypted. PkgToolBox parses it only when the entry is not flagged encrypted and refuses otherwise, and Coverly must do the same. applicationCategoryType values are not verified and the sources disagree. Demo: no known flag (heuristic only).

**Finding the base title.** titleId PPSAxxxxx is shared by base, patch and DLC. contentId = [region+publisher 6]-[PPSA 9]_00-[16-char label] (e.g. UP4433-PPSA17221_00-MINECRAFTPS50000). addcont.serviceIdForSharing lists the extra SKU service IDs (e.g. UP4433-CUSA00744_00, UP4433-PPSA19634_00), which is useful for linking cross-gen DLC. Where present, conceptId groups SKUs (unverified).

**Version.** param.json: contentVersion 'NN.NNN.NNN' (game or patch version), masterVersion 'NN.NN', originContentVersion/targetContentVersion (patches only), requiredSystemSoftwareVersion, sdkVersion. Plaintext in folders. In a PKG it is plaintext only if the param.json entry is not encrypted.

**What emulators and frontends expect.** Experimental and not standardised. SharpEmu's ParamLoader reads titleId and takes the version from contentVersion, then masterVersion, then targetContentVersion. ps5upload strips originContentVersion and targetContentVersion so a merged patch image launches as a base. Sibling -patch/-UPDATE folders and an addcont/<ID>/<label> tree are assumed by analogy with shadPS4 and not verified in a PS5 emulator. Jailbroken consoles (etaHEN, itemzflow) manage base, patch and DLC storage themselves.

**Naming conventions.** Assumed to mirror PS4 ('<CONTENT_ID>-A####-V####.pkg', 'PPSA01234 [v01.043] [Update]', '-patch', '(DLC)'); not verified. No No-Intro or Redump digital DAT for PS5 was confirmed. Redump covers PS5 discs.

**Confidence.** Medium-high: the FIH/CNT offsets and the encrypted-param.json refusal (PkgToolBox source), the patch fields and addcont.serviceIdForSharing (ps5upload source and tests), and the version fallback (SharpEmu source). Low: applicationCategoryType, DLC identification, emulator folder conventions and filename conventions. The ps5devwiki and gist claims were not re-checked.

## Xbox 360 (STFS CON/LIVE/PIRS packages, GoD, XEX, disc ISO/XISO)

**Formats.** STFS/XContent packages with no extension (magic 'CON ', 'LIVE' or 'PIRS' at 0x000). The usual filename is the 40-hex content ID, which is the SHA-1 at 0x32C, or a TU name such as 'TU_xxxxxxxx' or 'tuXXXXXXXX_YYYYYYYY'. Other forms: Games on Demand (an XContent header file plus a <name>.data/ folder with Data0000..DataNNNN, i.e. SVOD); extracted folders with default.xex; full disc ISO/XISO (XGD2/XGD3).

**Telling base / update / DLC / demo / revision apart.** No keys needed: the whole XContent header is plaintext, and only the RSA signature would need checking, which Coverly never does. VERIFIED against xenia src/xenia/vfs/devices/stfs_xbox.h (XContentHeader is 0x344 bytes, then XContentMetadata). Fields: magic at 0x000 ('CON '=0x434F4E20 console-signed; 'LIVE'=0x4C495645 / 'PIRS'=0x50495253 Microsoft-signed); content_id SHA-1 at 0x32C; header_size u32 at 0x340; content_type BE u32 at 0x344; metadata_version at 0x348; content_size u64 at 0x34C. An embedded XEX execution_info starts at 0x354: media_id 0x354, version 0x358, base_version 0x35C, title_id 0x360, platform 0x364, executable_type 0x365, disc_number 0x366, disc_count 0x367, savegame_id 0x368. Content types, VERIFIED in xenia src/xenia/xbox.h XContentType: 0x00000001 SavedGame, 0x00000002 MarketplaceContent = DLC, 0x00000003 Publisher, 0x00001000 Xbox360Title, 0x00004000 InstalledGame, 0x00005000 XboxTitle (original Xbox), 0x00007000 GamesOnDemand = base, 0x00009000 AvatarItem, 0x00010000 Profile, 0x00020000 GamerPicture, 0x00030000 Theme, 0x00040000 CacheFile, 0x00050000 StorageDownload, 0x00080000 GameDemo = demo, 0x000A0000 GameTitle, 0x000B0000 Installer = Title Update, 0x000C0000 GameTrailer, 0x000D0000 ArcadeTitle = XBLA base, 0x000E0000 XNA, 0x02000000 CommunityGame (indie). Coverly should keep base (0x7000/0xD0000/0x4000/disc), TU (0xB0000), DLC (0x2) and demo (0x80000) and ignore the rest. Disc/XEX: XEX2 magic 'XEX2' at 0; optional header ID 0x00040006 = Execution Info (media_id, version, base_version, title_id, platform, executable_type, disc_number, disc_count, savegame_id). The header area is plaintext; the PE image is encrypted/compressed and not needed. For disc ISO/XISO, Coverly must locate default.xex in the XDVDFS filesystem (no keys needed) and read its Execution Info.

**Finding the base title.** Match on equal Title ID: BE u32 at 0x360 in STFS, also in XEX Execution Info. There is no id arithmetic: the high 16 bits are the publisher code as 2 ASCII letters (0x4D53 = 'MS'), the low 16 bits are the game number. Media ID (0x354) tells apart the disc/edition a TU was built for. A TU is only valid for the base with the matching media ID, and its base_version must match. This matters for GOTY editions and re-releases that share a Title ID. DLC normally ignores media ID. Human-readable labels: display name at 0x411 is UTF-16BE, 9 locales x 128 chars = 0x100 bytes per locale (CORRECTED from 0x80; verified in xenia struct). Title name at 0x1691 is UTF-16BE, 64 chars = 0x80 bytes. Metadata v2 adds 3 more display-name locales at 0x541A, inside the shrunken thumbnail area (thumb length 0x3D00 instead of 0x4000).

**Version.** STFS: Version at 0x358 and Base Version at 0x35C (copy of the XEX execution info). XEX version is a BE u32 packed as major(4) | minor(4) | build(16) | qfe(8) from the most significant bits, e.g. 2.0.12.0. The TU number ('TU5') usually only shows up in the display name; to compare, use Version for the same Title ID + Media ID. GoD/disc version comes from XEX Execution Info.

**What emulators and frontends expect.** Console/Aurora/FSD: Content/0000000000000000/<TitleID>/<ContentTypeHex 8 digits>/<file>. TU goes in .../000B0000/, DLC in .../00000002/, GoD in .../00007000/<header> + <header>.data/, XBLA in .../000D0000/. Profile-bound content goes under Content/<ProfileXUID>/. CORRECTED, medium confidence: the common community rule (consolemods 'Manually Installing Title Updates') puts lowercase-named 'tu...' TU files in Content/0000000000000000/<TID>/000B0000/ and uppercase 'TU_...' files in the Cache folder. The original finding had this reversed. I could not open the page itself (Cloudflare blocked it), only search snippets. Xenia/Xenia Canary: content_root (config [Storage]) /<XUID or 0000000000000000>/<TitleID>/<ContentTypeHex>/<package>/, where the package is extracted to a folder. Canary's 'File > Install Content' takes STFS TU/DLC packages and extracts them into the right folder (confirmed in community guides). Xenia launches ISO, a GoD header file, or default.xex. The claim that 'Xenia loads TUs only when media ID matches' could not be verified in source. Treat it as a console rule, which Xenia probably also enforces through the XEX patch base-version/digest check.

**Naming conventions.** Console dumps keep their hex/TU filenames, and users rename them freely. Redump disc naming: 'Halo 3 (USA, Europe) (En,Ja,...)' plus (Rev N), (Disc N), (Demo), (Kiosk). No-Intro has a 'Microsoft - Xbox 360 (Digital)' DAT (it exists on DAT-o-MATIC), but I did not confirm its TU/DLC tag strings, so trust header bytes over filenames. Fallback regex: /\bTU ?\d+|Title Update/i -> update; /\bDLC\b|Add-?On/i -> DLC.

**Confidence.** High for header offsets, content type enum, Title ID/Media ID linking and UTF-16BE names (verified in Xenia source). CORRECTED: display name is 0x100 bytes per locale, not 0x80. Medium for the lowercase/uppercase TU placement (reversed from the original claim) and for Xenia enforcing media ID. Low for No-Intro digital tag strings.

## Xbox One / Xbox Series X|S (XVD/XVC packages, MSIXVC)

**Formats.** XVD/XVC container: RSA signature 0x000-0x1FF, then the header with magic 'msft-xvd' at file offset 0x200. Files are usually extensionless and GUID-named, sometimes .xvd/.xvc/.msixvc.

**Telling base / update / DLC / demo / revision apart.** VERIFIED against emoose/xvdtool LibXboxOne/XVD/XVDStructs.cs. Offsets in the struct comments restart at 0 AFTER the 0x200-byte signature, so file offset = 0x200 + listed offset. Fields: Magic +0x0; VolumeFlags +0x8 (bit 2 = EncryptionDisabled); FormatVersion +0xC; VDUID (ContentId) +0x20; UDUID +0x30; Type +0x80 (0 Fixed, 1 Dynamic); ContentType +0x84; SandboxId char[16] +0x18C; ProductId GUID +0x19C; PDUID (BuildId) +0x1AC; PackageVersion1..4 u16 +0x1BC..+0x1C2; RequiredSystemVersion1..4 +0x294. All of these are plaintext and readable without keys. ContentType values VERIFIED in XVDEnums.cs: 0x01 Title = game; 0x06 Application; 0x18 AppDlc, 0x19 TitleDlc, 0x1A UniversalDlc = DLC; 0x1E KioskContent; 0x0B Updater / 0x0C OfflineUpdater = system updaters, not game updates; 0x08/0x09/0x0A X360STFS/X360FATX/X360GDFX = 360 backward-compat; 0x02/0x03/0x07 OS volumes. The XvcInfo block (ContentID, Description, Version, RegionCount) lives in the XVC metadata pages. It is probably readable without keys (xvdtool prints it for encrypted packages), but this was not confirmed. Files inside the XVC, including appxmanifest.xml/MicrosoftGame.config, are encrypted with CIK keys and are off-limits.

**Finding the base title.** Update to base: same VDUID/ContentId and ProductId, higher PackageVersion and new PDUID. There are no separate delta files on disk; the update replaces the whole package. DLC to base: the plaintext header has no parent field, because the relationship sits in the encrypted manifest. Without keys, link through an external ProductId -> parent catalog (e.g. Store catalog / dbox.tools), the folder, or the filename. Sharing a SandboxId alone does not prove a parent relationship.

**Version.** PackageVersion: 4 u16 at +0x1BC (file 0x3BC). xvdtool prints them in reverse storage order (Version4.Version3.Version2.Version1). PDUID identifies the exact build.

**What emulators and frontends expect.** No usable retail emulator. On console, content is flat GUID-named XVC files on the drive with an index. Coverly should only group by ProductId/ContentId and show base/DLC/versions as information, with no install step.

**Naming conventions.** Redump has disc DATs for Xbox One and Series that use standard (Rev N)/(Disc N) tags. There is no common digital TU/DLC DAT. Filename fallback: /v?\d+\.\d+\.\d+\.\d+/ -> version; /DLC|Add-?On|Season Pass/i -> DLC.

**Confidence.** High for offsets and enum (verified). CORRECTED: offsets are relative to 0x200, so add 0x200 for file offsets. Medium for the update model. Low for DLC-to-base linking without keys.

## Retro cartridge systems: revisions and versions (NES, SNES, Genesis, GB/GBC, GBA, N64, NDS, ...)

**Formats.** .nes .sfc/.smc .md/.gen/.bin .gb/.gbc .gba .n64/.z64/.v64 .nds .pce .sms/.gg .a26, often zipped or 7z.

**Telling base / update / DLC / demo / revision apart.** All plaintext. These systems have no updates or DLC, only revisions, regions, betas/protos/demos and alt dumps. Header version bytes (offsets checked against the cited docs): SNES header version byte = header base + 0x1B, i.e. file 0x7FDB (LoROM) / 0xFFDB (HiROM), +0x200 if there is a copier header. Genesis serial at 0x180, 14 bytes 'GM XXXXXXXX-YY', where YY = revision. GB/GBC 0x14C = mask ROM version. GBA 0xBC = software version. N64 0x3F = ROM version (.z64 big-endian order; byteswap .v64/.n64 first). NDS 0x1E = ROM version. NES iNES/NES 2.0 has no version byte. Primary method: CRC32/SHA1 match against No-Intro DATs. P/C DATs (cloneof) or retool clone lists give the parent. Demo/beta/proto status comes only from DAT tags.

**Finding the base title.** Use the No-Intro parent/clone or retool clone lists. Fallback: the No-Intro name with every (...)/[...] stripped and normalized. Inside a group: region = edition; Rev/v = version; Beta/Proto/Demo/Kiosk/Sample = flagged variants; [b] and TOSEC/GoodTools [h]/[t]/[f] = excluded or flagged; (Alt) = duplicate dump.

**Version.** No-Intro tags '(Rev 1)', '(Rev A)', '(v1.1)'. An untagged name is the first release. Header bytes are the fallback. Order: untagged < Rev 1 < Rev 2; compare v numbers numerically.

**What emulators and frontends expect.** Nothing to install; each revision is its own file in roms/<system>/. Coverly: one card with a versions dropdown and one shared cover. RetroArch thumbnails are keyed by the exact No-Intro name (characters &*/:`<>?\| become _), so keep the exact name for thumbnails and the stripped name for grouping.

**Naming conventions.** No-Intro order: Title (Region) (Languages) (Version) (Devstatus) (Additional) (Special) (License) [Status]. Examples: 'Sonic the Hedgehog (USA, Europe) (Rev 1)', 'Game (Japan) (v1.1)', '(Beta 2)', '(Proto)', '(Demo)', '(Kiosk)', '(Sample)', '(Alt)', '(Unl)', '(Pirate)', '[b]', '[BIOS]'. GoodTools/TOSEC: (U)(E)(J) [!] [a] [b] [h] [t] [f] [T+Eng] (V1.1)/(PRG1). Grouping strip regex: /\s*[\(\[][^\)\]]*[\)\]]/g; version regex: /\((Rev [0-9A-Z]+|v\d+(\.\d+)*[a-z]?)\)/i.

**Confidence.** High. Offsets match the standard docs. I did not refetch them this pass, but they are consistent with my existing knowledge of these docs. Added the copier-header (+0x200) and N64 byteswap caveats.

## Retro disc systems: revisions and versions (PS1, PS2, Saturn, Sega CD, Dreamcast, GameCube, Wii, PCE CD; Redump)

**Formats.** .cue/.bin, .chd, .iso, .gdi, .cdi, .rvz/.gcz/.wbfs/.ciso, .pbp, .m3u.

**Telling base / update / DLC / demo / revision apart.** All plaintext; no keys needed. GC/Wii header, VERIFIED on wiibrew Wii_disc: 0x000 disc/system ID, 0x001-0x002 game code, 0x003 region, 0x004-0x005 maker, 0x006 disc number, 0x007 disc version, 0x018 Wii magic 0x5D1C9EA3, 0x01C GC magic 0xC2339F3D. The header is in the unencrypted system area; only Wii partition data is encrypted. On RVZ/WBFS/GCZ the header can still be read without keys (RVZ stores it raw at the start; WBFS keeps the disc header at its first sector). PS2 SYSTEM.CNF: 'BOOT2 = cdrom0:\SLUS_123.45;1' and 'VER = 1.00'. CORRECTED: the 'BOOT = cdrom:\...' form is PS1, and PS1 SYSTEM.CNF has no VER line. Dreamcast IP.BIN, VERIFIED on dreamcast.wiki: product number 0x40-0x49, version 0x4A-0x4F ('V1.000'), date 0x50. Saturn IP.BIN: product number 0x20 (10 bytes), version 0x2A ('V1.000'), date 0x30. Sega CD: 'GM XXXXXXXX-YY' at 0x180 in the system area, like Genesis. PCE CD has no version field; use the DAT. Primary method: Redump hash (track SHA1, or CHD raw SHA1). Wii 'update partition' = system menu update, ignore it. DROPPED: 'SCUS-9xxxx means demo' is wrong; many retail first-party US games are SCUS-94xxx (e.g. Final Fantasy VII = SCUS-94163). Only Japanese PAPX-9xxxx is a fairly reliable demo prefix; otherwise use Redump tags.

**Finding the base title.** Redump DATs have no cloneof, so use retool clone lists. Fallback: the name with tags stripped. Secondary key: serial / Game ID. Same serial with a different version = revision. GC/Wii: chars 0-2 (system + game code) are stable across regions, char 3 is the region, 4-5 the maker, byte 0x007 the revision. Multi-disc: same title with (Disc N) = one game, N parts.

**Version.** Redump '(Rev N)', '(v1.03)'; PS2 SYSTEM.CNF VER; GC/Wii 0x007; DC IP.BIN 0x4A / Saturn 0x2A version string. Untagged = original.

**What emulators and frontends expect.** No install step. Multi-disc: an .m3u listing the cue/chd files (RetroArch, ES-DE, DuckStation). ES-DE also supports a folder named 'Game.m3u' that contains the discs and the .m3u. Dolphin shows Game ID and a Revision column. Coverly: one card per game with revisions/regions and discs as children, and offer .m3u generation.

**Naming conventions.** Redump: 'Title (Region) (Languages) (Version) (Additional) (Disc N)', e.g. 'Final Fantasy VII (USA) (Disc 1)', 'Metal Gear Solid (USA) (Rev 1)', plus (Demo), (Kiosk), (Beta), (Proto), (Alt), and (EDC) on PS1. Budget-label tags such as '(Greatest Hits)'/'(Platinum)' appear in some sets, but Redump often expresses them only as Rev/serial, so do not rely on them (unverified). Treat '(Disc \d+)' as a part, not a version.

**Confidence.** High for the GC/Wii header and DC IP.BIN (verified) and for Redump tag semantics. Medium-high for the Saturn 0x2A version field. CORRECTED: PS2 BOOT2/cdrom0 syntax. DROPPED: the SCUS demo heuristic. Low for budget-label tags.
