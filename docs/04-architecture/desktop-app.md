# Desktop App (Tauri shell, IPC and UI state)

> **TL;DR.** The desktop app is a thin Tauri 2 shell over `coverly-core`. Opening a library scans it once into a compact `LibraryView` that the webview browses entirely in memory (filters, facets, sort, folder tree are pure TypeScript). The backend keeps the paths: the webview asks for art, identification and "reveal" by `(generation, entry id)`, never by path. Fills run as one backend job at a time (dry run → review → apply, pausable and resumable); only the entries a job touched are re-scanned and pushed to the webview. Settings (M5) are one typed `settings.json` edited from a Settings screen, applied live (theme, language, log level) or on the next open/job; see [settings.md](./settings.md). Updates (M7) are checked, downloaded and installed from Rust, never while a fill job runs; see [updates.md](./updates.md). A folder with no known layout is not a dead end: the app offers to organise its loose ROMs into one folder per system (proposal → apply → open, undoable); see [Organise](#organise) and [organize.md](./organize.md). In a plain browser the same UI runs on a deterministic mock backend. Spec: [§6, §7, §8, §9, §11](../superpowers/specs/2026-10-15-coverly-roms-design.md). Code: `src-tauri/src/`, `src/ipc/`, `src/stores/`, `src/lib/`, `src/components/library/`, `src/components/settings/`, `src/components/organize/`.

Event `library-scan-progress` → `{ generation, done, total, folder, roms }`: once before the first system folder, then after each.

Job events: `fill-job-progress` → `{ job, phase (gather/apply), done, total, label }` (throttled, ~20 a second, first and last always); `fill-job-changed` → `JobView` on every state change; `library-entries-updated` → `{ generation, entries: EntryArtUpdate[] }` after a job or a drawer action wrote (the UI ignores another generation).

Settings event: `settings-changed` → `Settings` after every saved update or reset (the log level is applied at the same time).

Update event: `update-progress` → `{ downloaded, total }` while an update downloads (throttled to ~10 a second, the last always).

Organise events: `organize-progress` → `{ plan_id, phase (walk/identify/dats/hash/apply), done, total }` (at most every 100 ms; phase changes and ends always); `organize-changed` → `OrganizeJobView` when an apply or resume ends (`done`, `paused`, `cancelled`, `failed`).

Errors are `{ "code": "<kebab-case>", "detail"?: … }`; the UI shows `errors.<code>` from `locales/{en,es}/ui.json` (`src/ipc/errors.ts`). Codes are stable.

## Generations

Every `open_library` takes a new generation. A newer open supersedes an older one still scanning (`superseded`; the UI ignores it), and calls that name an older generation get `stale-library`. A failed open keeps the library that was already open.

## Fill jobs

State machine (`src-tauri/src/jobs/mod.rs`):

```text
gathering → planned | paused(gather) | cancelled | failed
planned   → applying (run) | cancelled
applying  → done | paused(apply) | cancelled | failed
paused    → gathering | applying (resume) | cancelled
```

- **One job at a time.** A new `start_fill` is refused (`job-running`) while a job gathers or applies; otherwise it replaces the job (its journal stays for Undo) and older ids become `stale-job`. Drawer writes take the same writer slot, so a drawer write and a job never write at once.
- **Events.** Progress is throttled (~20/s, first and last always). After each write batch the job emits `written` (the touched entries are re-scanned and pushed as `library-entries-updated`) **before** `changed`, so the grid is up to date when the panel shows the new totals.
- **Decisions** are recorded on a `planned` job before Run (`decide_fill`). The app writes the `auto` items plus the review items the user accepted or re-picked; undecided review items are skipped as `skipped-review` (D20). The CLI keeps D14.
- **Pause and resume.** A rate limit, going offline or a full/read-only/vanished volume pauses the job with a reason (`paused.kind`: `rate-limit`, `offline`, `volume`). Resume after an apply pause finishes the not-attempted items into the **same journal** (`Writer::resume`), so one Undo reverts both runs (D21); resume after a gather pause re-runs the dry run (cached candidates) and clears decisions.
- **Undo** = the newest not-undone journal **of the open library** (`list_jobs` + `undo_job`), refused with `job-running` while a job gathers, applies or is paused. Files the user changed after the job are kept and counted as `kept`.
- **Crash safety.** Worker phases are guarded: a panicking worker ends the job `failed` instead of leaving it busy forever.
- **Re-scan of touched entries.** `subset_scan` re-scans only the folders of the written entries and `resolve_art` re-resolves their art; `refresh_entries` installs a new `Session` for the **same** generation and returns `EntryArtUpdate`s (no full re-open, no new generation).

## Organise

Organising a loose pile is described in [organize.md](./organize.md); this is the app side (`src/screens/OrganizeScreen.tsx`, `src/components/organize/`, `src/stores/organizeStore.ts`).

- **Entry points.** On `no-profile` the Start screen calls `probe_folder` and, when the folder holds ROM-like files, replaces the error with an offer (`OrganizeOffer`): *Organise this folder…* / *Choose another folder*; a folder that only holds system folders offers *Open as organised by system* with a layout `<select>` instead; broad roots get a warning line; counts are a lower bound when the probe stopped at 5 000 entries. A library whose scan found loose ROMs (`loose_files > 0`) shows *Organise loose files…*, which opens the screen with the library root as source and target and the library's layout locked. A folder found by the weak `system-folders` detection rule is shown as a suggestion. The job history (`JobsPanel`) labels organise jobs, and an interrupted one offers *Resume*, which continues on the organise screen; every organise row that is not undone offers *Undo* (with a confirmation) through `organize_undo`, which lists newer jobs that wrote under it and offers *Undo all in order*; the open library rescans when the panel closes. The library's *Undo last job* is for fill journals only, so it never moves ROMs from under the open library.
- **Proposal** (`navStore.screen = 'organize'`). Options bar (`OptionsBar`: layout, target, inside the ROMs folder or directly here, move/copy — move disabled with the reason when the source is read-only — and names); every change re-plans. A summary line, the plan warnings (catalogues not consulted, target already another layout, move unavailable), one `<details>` per system (`SystemGroups`) with source → target, confidence and the "why", review items bucketed by candidate set with one `<select>` + *Apply to all* per bucket (`ReviewBuckets`), and the items left in place with their reason (`LeftInPlace`; unknown items keep a system `<select>`). Lists render 200 rows and a *Show {n} more* button; groups start open only for plans of 200 rows or fewer. *Export plan (JSON)* saves the plan through `organize_export_plan`.
- **Apply, result, undo** (`OrganizeResult`). Apply shows progress and a cancel button; a pause offers *Resume*. The result shows moved/copied/skipped/failed counts and the per-item list, **Open library** (`libraryStore.open(target, layout)`, so no detection is needed) and **Undo**. When newer jobs wrote under the organised folder, undo names them and offers *Undo all in order*. The screen stays open while files are moving.
- **Store.** `organizeStore` keeps `status` (idle, planning, ready, applying, done, paused, error), the request, `planId`, the plan, the decisions by item id, progress, the job view, the last undo and `locked`. It sends only `plan_id` + decisions; a sequence number drops plan answers a newer request superseded, and progress events of another plan are ignored. Apply, resume and undo drop every plan the backend kept, like Rust.
- **Guards.** Apply, resume and undo take the `JobManager` manual-write guard: refused with `job-running` while a fill gathers, applies or is paused, and fills are refused while an organise apply runs. Job history entries carry `kind` (`fill` / `organize` / `dedupe`) and `undoable`.
- **Duplicates step.** The options bar has a *Duplicates* picker (*Set aside* · *Report only* · *Don't look*, default from `dedupe.organize_step`; the request's `duplicates` field). The summary adds "Duplicates: {n}" and "Already in your library: {n}", a section between the review buckets and the items left in place renders the groups with the dedupe `DupGroup` (capped at 200 rows), and the primary button reads "Organise {n} files and set aside {m}". An archive that would be extracted and is a duplicate shows as set aside, not extracted. The result counts `quarantined` and `trashed` outcomes.
- **Settings link.** The header has *Organise settings* (`SettingsLink`, disabled while applying), which opens Settings › Organise. Before opening it the store keeps `organizeStamp(settings)` (`src/lib/settingsStamp.ts`: the `organize` group and `dedupe.organize_step`); the first stamp stays until a new dry run starts; one taken while a dry run is in flight stays with the plan it shows, and a cancelled or failed dry run puts back the stamp of the plan still on screen. Back returns to the same proposal, and if the stamp changed the ready proposal says "The organise settings changed. Scan again to use them for what you have not chosen here." with the *Scan again* button.

## Duplicates

The finder and its safety rules are in [dedupe.md](./dedupe.md); this is the app side (`src/screens/DuplicatesScreen.tsx`, `src/components/dedupe/`, `src/stores/dedupeStore.ts`, `src-tauri/src/dedupe/`).

- **Entry points.** The library toolbar's outline button (lucide `Copy`) reads "Find duplicates", then "Duplicates {count}" once a plan of that library has extras (icon only below 1180 px). It opens `navStore.screen = 'duplicates'` for the library root. The Organise proposal has its own duplicates step (above). The job history labels dedupe jobs "Duplicates"; *Resume* and *Undo* go through the organise branches (`dedupe_resume`, `organize_undo`), the fill undo filter skips them, and an undo report lists each copy the Trash no longer held ("Not in the Trash any more: {path}"). Settings has a Duplicates tab, and the screen's header opens it with *Duplicates settings* (below).
- **Commands and events.** `dedupe_plan(root, opts)` (emits `dedupe-progress` per phase), `dedupe_cancel`, `dedupe_regroup`, `dedupe_set_keeper`, `dedupe_skip_group`, `dedupe_skip_system`, `dedupe_reset_choices`, `dedupe_apply(plan_id)` (emits `dedupe-progress`, then `dedupe-changed`), `dedupe_cancel_apply`, `dedupe_job`, `dedupe_resume(job)`, `dedupe_export_plan`, and `reveal_path`. Undo is `organize_undo`, which calls `undo_job_with(…, &OsTrash)`. `DedupeManager` keeps the four newest plans (`KEPT_PLANS`), throttles progress like organise and runs apply behind the `JobManager` write guard: no dedupe apply while a fill or an organise job writes or is paused, and the other way round. The planner uses `ArchiveEntryListing::with_tools` with the organise external-tools setting and `ReaderDiscProbe`. Error codes added: `no-dedupe-plan`, `keeper-required`, `quarantine-in-system-folder`. The plan view carries `trash_available` (`OsTrash.available(root)`).
- **Screen states** (`dedupeStore.status`): `idle | planning | ready | applying | done | error`. *Planning* shows the phases in order with checks (Listing, Sizes, Fingerprints, Serial numbers, Catalogues). *Ready* shows the summary sentence (Archivo on the count), the options strip (`DedupeOptions`: levels as a multi `ToggleGroup` with the delta of a change next to it and announced, the action radio, *Change…* for the quarantine), the conflicts alert, one `SystemSection` per system, *Unchanged* (`UnchangedList`, with reasons) and a sticky bar (verb + exact count, *Export report*, bytes "out of ROMS/"). *Applying* uses `<Progress slots={16}>` and Cancel. *Done* is `DedupeResult` (undo, resume after a pause, "The card is just as full until you empty…" on the same volume, *Find covers* when art left with a copy). The empty state is `EmptyState` ("This shelf is in order."); the error state says what failed and "Nothing was moved.", with a retry. ⌘/Ctrl+R plans again.
- **Shelf and tray** (`DupGroup`, `KeeperRow`, `TrayRow`). Each group is a shelf (the keeper, with the 3 px Buckram cap and its one-line reason) over a recessed tray of the copies that go, each with its destination in mono and a visible "Keep this one" radio. Changing the keeper slides the cap, drops the old keeper into the tray and is announced in a live region with an undo; no motion under reduced motion. Relation and state always carry a lucide icon and a word (`Copy` exact, `Disc3` other format, `History` other version, `CircleHelp` not confirmed, `TriangleAlert` conflict); the confidence number is in the badge tooltip. "Leave this game alone" skips a group; each system's menu has "Leave {system} alone" and "Apply the rules again in {system}". A conflict (`ConflictGroup`) has no radio and lists each save with size, date and *Open folder*. A tie the reader cannot change does not invite a pick.
- **Systems** (`SystemSection`, `useGroupWindow`). The trigger is a sentence ("Master System: 23 games, 23 copies") with the bytes in the right-aligned size column. Systems with conflicts open by default; a closed system mounts no rows; past 200 groups a small in-house window over measured row heights keeps only the visible rows plus a margin in the DOM, and keyboard focus follows the data.
- **Confirms.** An apply above 500 files, above 25 % of the library's bytes, with a confirmed big group, or to a quarantine on another volume asks first. The Trash confirm names the count and bytes and says that undo brings the files back from the Trash and that emptying it makes that impossible. The Trash option is disabled with its reason when `trash_available` is false.
- **Store.** `dedupeStore` keeps the request, `planId`, the plan view, the picks and skips, progress and the phases done, the job view, the last undo and, per library root, the count the toolbar shows. It sends only `plan_id` + decisions; a newer request supersedes older answers, and leaving the screen cancels a plan still being made. Undo drops the toolbar count.
- **Settings tab** (Settings › Duplicates, `DuplicatesSection.tsx` over `DedupeSettings.tsx`). On top (`DedupeCommon`), what the screen starts with: the action radio (set aside / Trash), the quarantine folder with *Choose…* (the default shown as `<library>/_Duplicados`) and "One ROM per game". Under *Advanced options* (`DedupeAdvanced`): the three level switches, the keeper rules as a reorderable list with `ReorderAnnouncer` (the region rule shows the Matching region order read-only, with a link to change it there), the container order editor and the excluded systems. The Organise step (`organize_step`) lives in the Organise tab; a link points there. The screen's header has *Duplicates settings* (`SettingsLink`); before opening it the store keeps `dedupeStamp(settings)` (`src/lib/settingsStamp.ts`: keeper rules, container order, exclusions, quarantine name, region order). Back returns to the same plan, and if the stamp changed the screen says "The duplicates settings changed. Look again to use them." with a button that plans again. The action, levels, one-ROM switch and folder are not in the stamp: the screen sets them itself. `src/lib/settingsRules.ts` mirrors the Rust checks: no repeated rule, no custom quarantine inside a system folder.

## Security

- The webview never sends a path except the folder the user picked. Art and reveal resolve paths from the scan, canonicalise them and refuse anything outside the canonical library root (symlinks included) — `outside-library`. Art over 20 MiB is refused.
- The image picker and the save dialog run in Rust (`DialogExt`); the webview never sends a path. Picked files are read up to 20 MiB and always decoded and re-encoded. Candidates are addressed by `(job, item, candidate)` or `(generation, entryId, media, candidate)`.
- No asset protocol, no `fs` plugin, no `updater:` permission (updates run from Rust with our endpoint and key); capabilities are `core:default` + `dialog:allow-open`; the opener plugin is used from Rust only. CSP `img-src 'self' data: blob:`. Pinned by `src-tauri/tests/config_security.rs`.
- File names are hostile: React text only, `unicode-bidi: plaintext`, truncated with `title`; the mock's SVG escapes them. Only PNG/JPEG/WebP/GIF bytes become images (`sniffImageMime`), never SVG from disk.

## System icons

Every place that names a system shows its icon beside the name: the sidebar's Systems tab, the filter panel, the Details system column and group rows, the cover meta line, the inspector, Reports, the fill wizard's summary and review queue, and the organise screen's group triggers and review buckets. Spec: [`2026-10-18-system-icons-and-views.md`](../superpowers/specs/2026-10-18-system-icons-and-views.md) §A.

- **Source:** 41 silhouettes from the RetroArch Assets XMB "Monochrome" theme (CC BY 4.0, pinned commit), attributed in `THIRD-PARTY-NOTICES.md` and `src/assets/system-icons/README.md`. They are neutral hardware shapes (pads, handhelds, computers, a cabinet), each audited for logos, wordmarks and badges; the trademark position is in `TRADEMARKS.md`.
- **Pipeline:** `pnpm system-icons` (`scripts/icons/systems.mjs`) fetches the pinned SVGs once, recolours every fill and stroke to `currentColor`, optimises with SVGO, crops the viewBox and writes the committed outputs: `src/assets/system-icons/<id>.svg`, its `README.md` (source, changes, audit table), `contact-sheet.html` (every icon at 14/16/20/48 px in both themes) and `src/components/system/systemIcons.generated.ts`. The app and the build never fetch icons. The script exits non-zero on any failed check; `systemIconsBuild.test.ts` and `systemIcons.test.ts` check the generator and the committed data: clean bodies (no scripts, ids or colours), valid viewBoxes, every source audited, no wordmark mapped to a silhouette, and every `systems.toml` id resolving to exactly one of an icon or an abbreviation.
- **Component:** `SystemIcon({ systemId, size = '1em', title?, className? })` (`src/components/system/`) draws the silhouette, the fallback or, for `systemId: null` (a folder Coverly did not recognise), a folder. The box is always 1.5 × its height wide, so a column of names lines up whatever the icon. Without `title` it is `aria-hidden`; with one it is `role="img"` with that label (lone icons only). `SystemLabel({ systemId, name, trailing? })` is icon + name, leading by default; trailing puts the icon after the name and keeps it decorative. `systemLookup.ts` finds the system for a folder where a surface only has the folder.
- **Fallback:** systems with no neutral silhouette (CPS1–3, MAME, DOS, ScummVM, EasyRPG… whose theme icon is a logo or wordmark) and user-defined systems get a Slot-shaped mount with an abbreviation (`systemFallbacks.ts`: `FALLBACK_ABBR`, else the first four letters of the id). From 20 px the mount has an outline, from 24 px its corners.
- **Switching an icon to the fallback:** remove the id from `SYSTEM_ICON_SOURCES` in `scripts/icons/systemIconsLib.mjs`, add an abbreviation to `FALLBACK_ABBR` (and the id to `WORDMARK_IDS` if the theme icon is a mark), run `pnpm system-icons` and commit the regenerated files. Adding a silhouette is the reverse, with an audit line for the new source file.
- **Colour:** icons inherit `currentColor`, so they follow the text they sit beside (`--cr-text-secondary` in most places, above 3:1 in both themes).

## Library views

Six views, switched from the toolbar or with ⌘/Ctrl+1–6: **Covers** (1), **Details** (2), **Columns** (3), **Gallery** (4), **Art slots** (5, `mounts` in code) and **Shelves** (6). The first four follow Finder's. Spec §B; components in `src/components/library/views/`, each taking `ViewProps` (`types.ts`): entries already in grouped order, the sections, the prefs and the open/select/preview callbacks. `LibraryScreen.renderView` picks the component.

- **ViewPrefs** (`src/lib/viewPrefs.ts`): `view`, `coverSize` (XS–XL; Covers, Shelves), `groupBy` (none, system, folder, region, art status, first letter), `art` (cover, title, screenshot; Covers, Shelves, Gallery), Details `columns` (order and widths; `name` can be moved, never hidden) and `density`, and `inspector` (docked pane; not in Columns or Gallery, which have their own preview). `viewStore` holds them; the toolbar's View options popover edits only the controls that apply to the current view.
- **Persistence:** `localStorage` key `coverly.views.v1` holds `{ last, byLibrary, order }`: prefs per library root (the 20 most recent), and the last ones used for a library seen for the first time. Everything read back is validated field by field against whitelists; an unknown value falls back to its default, broken JSON to the defaults. When the key is missing, the old `coverly.layout` is migrated: `list` opens Details, anything else Covers. Prefs load before the first paint and no-op writes are skipped.
- **Grouping and row model:** `groupEntries` (`src/lib/grouping.ts`) is a stable partition of the visible entries; groups come first and the current sort applies inside each group. Sections are index ranges, never copies. Art-status groups are frozen while a fill runs so games do not jump between groups. `buildRowModel` (`src/lib/rowModel.ts`) turns sections into header rows and rows of `perRow` items for the virtualisers, so a resize or size change never regroups. `useActiveRange` keeps the selected item rendered, and the sticky header in step with the scroll position.
- **Keyboard:** one model for every view (`useViewKeys` in `src/components/library/views/`, over the pure helpers in `src/lib/keyboardNav.ts`): arrows move, Home/End and Page Up/Down jump, Enter opens the game, Space opens Quick look (mid-word it continues the typed name), letters type ahead (500 ms buffer, ignoring region tags), ⌥↑/⌥↓ jump between groups, Tab always leaves the view. Each view only adds its own dimension: Columns →/← between panes, Gallery ←/→ along the filmstrip, Shelves ↑/↓ to the nearest game on the next shelf, Art slots ←/→ between slots and Enter on a slot opens it in the art workspace. `useViewShortcuts` (`src/hooks/`) handles ⌘1–6, ⌘+/⌘−/⌘0 (size, also ⌘/Ctrl + wheel or a pinch, one stop per 100 px), ⌘I (inspector); none of them act behind an open dialog, and size and inspector keys stand down in a text field. After a switch, focus moves to the new view, whose accessible name includes the view.
- **Adding a view:** add the id to `ViewId` and `VIEW_IDS` (that also gives it the next shortcut) and, if it docks the inspector, to `INSPECTOR_VIEWS`; write the component against `ViewProps`, using `useViewKeys` and a virtualiser over `buildRowModel` rows; add a `case` in `renderView`; add its toggle icon and tooltip in `ViewSwitcher` and its controls in `ViewOptions`; add `layouts.<id>` in `locales/{en,es}/ui.json`; test the component (keyboard, roles, `aria-rowcount`), extend `viewPrefs.test.ts` and `LibraryScreen.test.tsx` (switching, shortcut, persistence), and check it at 12k entries in the mock (mounted rows under 200, no long task over 200 ms).

## Settings screen

`src/screens/SettingsScreen.tsx`: General on its own; then three groups, Collection (Library, Organise, Duplicates, Profiles), Covers (Art, Matching, Sources) and App (Network, Safety, Advanced); then About (`src/components/settings/`). New tabs for collections, devices, saves or RetroAchievements join a group in `SETTINGS_GROUPS`. The tab list is one `tablist` (group headings are not `role="group"`); on a narrow window it becomes a row that scrolls inside itself and ←/→ move along it. Library keeps the scan options and the recent libraries; Organise and Duplicates have their own tabs. Each tab shows the common options and folds the rest under *Advanced options* (`AdvancedFold` in `Field.tsx`, with its count; the folded content stays mounted so drafts and ids survive, a field error opens it, and a closed fold with errors says so). Long help sits behind *More information* (`MoreInfo`). The search field (⌘F on macOS, Ctrl+F elsewhere, `/` outside a text field) matches labels, hints and keywords in every bundled language (`search.ts`, ranked by the UI language) over the static index in `registry.ts`; `registry.test.tsx` fails when a `setting-…` control has no entry or an entry has no control. Choosing a result opens its tab, opens its fold, focuses the control and marks it briefly. The Duplicates and Organise screens open their tab with `SettingsLink`, and Back returns focus to that link. Each field saves on change, or on blur for typed values. An invalid value keeps what was typed and shows `settings.field.<code>` next to it while the other fields still save. Scan-affecting changes with a library open show "Reopen the library to apply these changes." with "Reopen now". Theme (`<html data-theme>`) and language (`<html lang>`, `I18nProvider` + `pickLocale` for `auto`) apply live. Job events keep flowing while the screen is open. Credentials are write-only inputs. Profiles shows the built-ins read-only, with Duplicate, and an editor with a live path preview. About shows the version, the licence, the no-telemetry note and fixed links. The fill wizard takes its defaults from the settings (media, strategy, regions). With overwrite `ask` nothing is preselected. For a layout that reads `gamelist.xml`, the wizard notes that it is updated (with a backup).

## Mock adapter

`getBackend()` picks Tauri when `window.__TAURI_INTERNALS__` exists and lazily imports `src/ipc/mock/mockBackend.ts` otherwise (its own chunk). The mock serves seeded libraries from `generateLibrary` (mulberry32): `/mock/Fixture SD (12k)` (12,000 entries, 18 systems, mixed cover/screenshot/title, hostile names, dates over 3 years), `/mock/Small library` (240), `/mock/Empty library` (0), an unavailable `/Volumes/EJECTED` recent, and `not-found` for anything else. `pickFolder()` opens the 12k fixture; dropping a folder named `X` opens `/mock/X`. Art is an escaped SVG per entry; identify answers hash for `id % 3 == 0`, offline for `id % 3 == 2`.

Fill jobs in the mock (`src/ipc/mock/mockJobs.ts`, deterministic): an entry/media is `auto` when `(id + mediaIndex) % 10 < 7`, `review` when `7` or `8` (`8` = an unreleased-variant note), `none` when `9`; an `auto` item of an entry with `id % 13 === 0` fails on apply with `['no-art', 'network', 'decode', 'name-invalid'][id % 4]`; undecided review items are skipped; each write is journaled (`mock-0001`…) so Undo restores the previous marks, refused while a job runs or is paused and only for journals of the open library. Options: `pauseAfter` (the first apply of each job pauses with a rate limit after this many items; default 25, `null` = never) and `pick` (what "From file…" picks: `image`, `cancel`, `not-image`). Exports are downloaded through Blob URLs (`coverly-job-<id>.csv/json`, `coverly-audit.csv/json`). Each subscription is its own listener, like Tauri's `listen`, so React StrictMode's double connect keeps its events. Settings, custom profiles and credential presence persist in `localStorage` (`coverly.mock.settings`, `coverly.mock.profiles`, `coverly.mock.credentials` with booleans only). The validation rules are the TypeScript mirror of the Rust ones. Search by title answers three regional variants of the typed title. Updates follow `?mockUpdate=available|up-to-date|offline|bad-signature|no-key` (or localStorage `coverly.mock.update`; default `up-to-date`, so no startup banner), and `mountedVolumes` lists `/mock/Small library`. Organising (`src/ipc/mock/mockOrganize.ts`, deterministic) knows two piles that `openLibrary` answers with `no-profile`: `/Users/demo/Downloads/roms` (the shape of the owner's real sample: 16 ROMs for GBA/GB/GBC/SFC, 1 duplicate, 3 partial downloads, a `.DS_Store`) and `/Users/demo/Mixed` (4 sure ROMs, 2 for review, 1 unknown, 1 duplicate, 2 partial downloads). Apply runs in steps of 4 items with pause/resume and turns the pile into a library of the chosen layout; undo refuses while later jobs wrote under the target unless asked. Any other organise source is `not-found`. The mixed pile also holds an exact copy of a game in the mock library, which the duplicates step sets aside. Duplicates (`src/ipc/mock/mockDedupe.ts`, deterministic) give every library the `dedupeFixture` plan under its own root, keep plans by id like Rust (four at most), remember picks by path per library, and apply "moves" the extras out of the library: the next plan no longer finds them, and undo (through `organizeUndo`) brings them back from the quarantine or the Trash alike. `window.mockDedupeScenario({ empty, failPlan, trashAvailable, pauseAfter })` switches to the empty state, a failing plan, a volume without a Trash or a paused apply.
