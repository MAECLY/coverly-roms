## 1. Purpose

Today Coverly knows that a file is a base game, an update, a DLC or a demo (by the title id or `CATEGORY` it reads in clear), links an update or DLC to its base when both are in the pile, and lists it under the base in Organizar. On disk, though, everything still lands flat in the system folder (`3DS/Pokemon.cia`, `3DS/Pokemon update 1.cia`), retro revisions are unrelated files, and the library scan would list every update as a game of its own.

Part A turns the game into a folder, as Miguel decided on 2026-11-01:

```
ROMS/PS4/Hatsune Miku Project DIVA Future Tone (USA)/
    Hatsune Miku Project DIVA Future Tone (USA).pkg
    DLC/
        Hatsune Miku Project DIVA Future Tone (USA) - Song Pack 1.pkg
    Updates/
        Hatsune Miku Project DIVA Future Tone (USA) (v01.05).pkg
ROMS/PS4/Hatsune Miku Project DIVA Future Tone (USA) (Demo)/
```

It delivers: the profile option that turns the layout on; Organizar moving base, updates and DLC into it with full undo; versions and regions read from headers into the names; detection extended to every system that has updates or DLC; licences and system files recognised by name only and left where they belong; retro revisions grouped as versions of one game; and the minimal UI to see and switch it. Three rules carry over unchanged: **keys are untouchable** (never read, include, download or decrypt), **nothing is overwritten**, and **every change is undoable**.

## 2. The owner's asks (verbatim from `TODO.md` §2.1)

> ### Estructura maestra de la biblioteca (decidida con Miguel, 2026-11-01)
>
> - **Una carpeta por juego** con el juego base en su raíz, y dentro `DLC/` y `Updates/` (nombres fijos en inglés para que emuladores y herramientas los reconozcan; la interfaz los muestra traducidos).
> - **Demos aparte**, como juego independiente, con el sufijo `(Demo)` de No-Intro/Redump (no `DEMO`) para que se ordenen junto al juego; relacionadas con el base en la ficha, pero no dentro de su carpeta.
> - **Versión en el nombre** de cada actualización (`… (v1.05)`), sacada de la cabecera, para saber cuál es la más nueva.
> - **Regiones:** si hay el mismo juego en varias regiones, una carpeta por región con la región en el nombre (`… (USA)`, `… (Japan)`); cada actualización y DLC va con la región de su title ID.
> - **Revisiones retro** (`(Rev 1)`, `(v1.1)`) como versiones del mismo juego en la ficha (no como juegos distintos); en disco siguen siendo archivos sueltos salvo que el perfil pida carpetas.
> - La misma carpeta del juego es la que usará `Saves/` del bloque 5.
>
> ### Carpetas fijas y `Extras/` libre (decidido con Miguel, 2026-11-01)
>
> - **Carpetas fijas del juego:** `Updates/`, `DLC/`, `Mods/`, `Cheats/`, `Extras/` y `Saves/`. Siempre con ese nombre y en ese sitio, porque de ellas dependen la organización automática, la traducción a cada emulador (4) y las partidas (5). El usuario no crea carpetas nuevas a ese nivel; la interfaz las muestra traducidas.
> - **Licencias** (`.rap`, zRIF, `work.bin`, DLC de solo licencia `AL`): se reconocen y se dejan junto al archivo al que pertenecen, sin leerlas nunca.
> - **No son juegos:** actualizaciones de sistema y firmware (particiones de actualización de cartuchos 3DS/Wii, `PS3UPDAT.PUP`, `0004001B…`), cachés de shaders y configuraciones por juego del emulador: se reconocen y se dejan donde están.
>
> ### Tareas (las de la parte A)
>
> - [ ] Crear y respetar las carpetas fijas en Organizar y en la biblioteca, con deshacer.
> - [ ] Opción de perfil «carpeta por juego con `DLC/` y `Updates/`» para la biblioteca y los perfiles que la acepten.
> - [ ] Organizar: mover base, actualizaciones y DLC a la carpeta del juego con deshacer; demos a su carpeta `(Demo)`.
> - [ ] Nombres con versión y región sacadas de las cabeceras.
> - [ ] Extender la detección a todos los sistemas con actualizaciones o DLC (Tandas 1–3 y PSP, Wii/WiiWare…).
> - [ ] Revisiones retro agrupadas como versiones de un juego en la biblioteca y en duplicados.
> - [ ] Interfaz: el juego con sus actualizaciones y DLC plegados debajo, versión instalada y la más nueva disponible.

Workflow brief for this run (part A): the option is **on for the library (Coverly) profile and off by default for handheld profiles** whose frontend does not take folders as games; folder names fixed in English on disk and translated in the UI; **create only folders that get content**; scanning, Organizar and Duplicados never treat files inside the fixed folders as loose games nor as duplicates of the base; paths `<System>/<Game>/<Game>.<ext>`, `Updates/<Game> (vX.YY).<ext>`, `DLC/<Game> - <DLC name>.<ext>`; demos as `<Game> (Demo)` linked by name only; versions from headers (3DS/Wii U title version, Switch cnmt version when in clear, PS3/PS4/Vita/PSP `APP_VER`/`VERSION`, Xbox 360 STFS); region from the title id or product code; licences recognised **only by file name or extension, never opened**, moved with their file when unambiguous, else left in place; system updates, firmware, shader caches and per-game emulator configs recognised as «not a game» and left; retro revisions grouped in the library model and Duplicados (newest suggested, never both deleted), loose on disk unless the profile asks for folders; minimal UI in Organizar and Ajustes → Biblioteca. Not here: the six-views redesign, Mods/Cheats association, emulator translators, Extras CRUD.

## 4. Decisions

| # | Topic | Decision | Why |
|---|---|---|---|
| D1 | Where the option lives | New field `Profile.game_folders: bool` (serde default `false`; custom TOML key `game_folders = true`, copied by «duplicar perfil»). User override per profile in `OrganizeSettings.game_folders: BTreeMap<profile_id, bool>` (serde default empty, like `folder_names`); `Profile::uses_game_folders(&OrganizeSettings) -> bool` = override, else the profile's own value. `TargetLayout.game_folders` carries the resolved value into planning (for the layout the run uses, which `OptionsBar` can change per run). The option governs **only what Organizar creates**: the scan, the pile walk and Duplicados respect existing game folders **always**, whatever the option and whatever profile the library was detected as (D7–D9), so turning the option off, or a library detected as another profile, never makes updates count as games again. No `SETTINGS_VERSION` bump (additive, defaulted field; settings are not `deny_unknown_fields`, so an older build ignores the map). `ProfileFile::to_toml` writes `game_folders` only when `true` (older builds read the file unchanged otherwise). | The brief calls it a profile option; built-in profiles are code, so a user choice on them needs a settings override, the pattern `folder_names` already uses. Respecting folders regardless of the option is the brief's «RESPECT them everywhere». |
| D2 | The library (Coverly) profile | New built-in profile id **`coverly-library`** (not `coverly`: `ProfileStore::load` drops a custom profile whose id equals a built-in, and a user custom profile named «Coverly» would slug to `coverly`), display name **«Coverly»** (built-in names are untranslated product names; the UI shows it as it shows `Anbernic stock`). Migration guard: if a custom TOML with id `coverly-library` exists, it is **not dropped**: the loader keeps it under `coverly-library-custom` with a warning and rewrites settings references (`default_layout`, `default_profile`, `folder_names`, `game_folders` keys) in the same normalise pass; a test covers it. Values: `roms_root = "ROMS"`, folder naming like `anbernic-stock` (`PS4`, `3DS`, `SFC`, matching Miguel's `~/Documents/ROMS`) but **no `host_folders` merges** (`supergrafx → pcengine` and the like are device limits; the master library keeps every system in its own folder, and device translation is part B), `disc_layout = GameFolder { m3u_for_multi: true }`, `accepts_containers` zip + 7z, `game_folders = true`, art slots inside the game's own folder under a hidden `.media/` (`{system_dir}/{rel_dir}/.media/{stem}.png`, `-screenshot`, `-title`; `art_dir_names = [".media"]`). It is **never auto-detected** in part A: `rules_for("coverly-library")` returns no markers, so `detect()` keeps its current scores; the user picks it as the Organizar layout or the library's profile. Known side effect, accepted: a Coverly library holding `.media/` folders scores 30 for MinUI (`Marker::MediaDirs`) and opens as MinUI when «Perfil por defecto» is «Automático»; art paths are the same template, and the scan respects game folders whatever the profile (D1), so nothing is miscounted; Ajustes → Biblioteca lets the user pin `Coverly`. All other built-ins: `game_folders = false`. The contract sample's built-in list (`src-tauri/tests/contract.rs`, `contract.sample.json`) gains the profile. | Brief: on for the library profile, off for handheld profiles. ES-DE and Batocera show a folder with sub-folders as a folder, not a game (they need «directory as game» or a suffix, a part B translator); Onion, MinUI, muOS and the Anbernic stock launcher list files. Art in `.media/` is provisional until §3/§3.1 and part C decide the library's art store; it keeps images out of the scan and out of `Extras/` (which belongs to the user). |
| D3 | Fixed folder names | `consoles::FixedFolder { Updates, Dlc, Mods, Cheats, Extras, Saves }` with `dir_name()` = `Updates`, `DLC`, `Mods`, `Cheats`, `Extras`, `Saves` (exact English, this casing) and `FixedFolder::from_dir_name(&str)` matching **case-insensitively and exactly** (`updates`, `dlc` match; `Update`, `DLCs`, `Updates (old)` do not). A *game folder* is a directory directly under a system folder (or anywhere in a pile, D7) that has **exactly one base game at its root** (one ROM-like file, one sheet set, or the folder game itself) (§8.1). Holding a fixed folder is **not** enough: `SNES/Hacks/Mods/…` (a user's hack collection) is not a game folder, so nothing in it is hidden. A fixed folder directly under a **system** folder (Batocera `ps4/DLC/<title id>/`, batch 3 D16) is never a game's fixed folder: it keeps today's behaviour. On a case-sensitive volume holding both `DLC/` and `dlc/`, both are the DLC folder; Organizar fills the one whose name sorts first by bytes and never creates a third. | Fixed names are how part B translators and block 5 find content; case-insensitive matching because users and other tools write `dlc/`, and APFS/NTFS are case-insensitive anyway. Requiring a base keeps installed users' libraries from losing entries to a folder that merely happens to be called `Mods`. |
| D4 | Create only what gets content | Organizar creates `<Game>/` only when the item needs it, `Updates/` only for an update, `DLC/` only for a DLC. Never creates `Mods/`, `Cheats/`, `Extras/` or `Saves/` in part A (nothing goes into them yet). Each created directory is a journaled `Op::DirCreated`; undo removes it only when empty (existing rule). | Brief: no empty folders. |
| D5 | Target paths | With `game_folders` on, **for the systems that have updates, DLC or demos by header** (3DS, Switch, Wii U, Wii WAD, PS3, Vita, PSP, PS4, PS5, Xbox 360, Xbox One/Series: the D14 list), every game of that system (file, set, archive or folder game): base → `<System>/<Game>/<Game>.<ext>` (a disc set: its members inside `<Game>/`, as the disc `GameFolder` layout does now, with its `.m3u`); update → `<System>/<Game>/Updates/<Game> (v<version>).<ext>`; DLC → `<System>/<Game>/DLC/<Game> - <DLC name>.<ext>`; a **folder game** (PS3 JB, Vita app, Wii U loadiine, PS4 `CUSA…`) keeps its own folder as the game folder: base → `<System>/<Game>/` (the folder itself, renamed to `<Game>` only when names are «catálogo»), its update folder → `<System>/<Game>/Updates/<folder name>/`, its DLC folder → `<System>/<Game>/DLC/<folder name>/`. Profile rules that already place DLC elsewhere win (`dlc_folder` on Batocera, shadPS4 `-UPDATE` siblings: those profiles have `game_folders` off). With the option off, nothing changes. **Retro systems (no updates or DLC: Tanda 1 cartridges and discs) keep today's placement even with the option on** (loose files; discs keep the profile's `disc_layout`), which is the brief's «en disco siguen siendo archivos sueltos salvo que el perfil pida carpetas» read safely: one folder per NES ROM is a mass change the owner has not asked for in so many words (§13 Q8). The game folder name goes through the same rules as a stem: safe-name for FAT/exFAT and Windows (reserved names, `<>:"/\|?*`, control characters), trailing dots and spaces trimmed (the existing `target.rs` stem trim), NFC, and `DirIndex` (NFC, lower case) for reuse and collisions. For a folder game holding `Updates/`/`DLC/`, `folder_entry` (scan) and the dedupe folder unit measure and fingerprint the tree **without** the fixed folders, so a base's size, its exact key and its removal never include its children (D9). | Brief §2 paths. A folder game is already a folder: nesting `Game/Game/` would break PS3/Vita/PS4 loaders that look for `PS3_GAME/`, `sce_sys/` at the folder root. Known limit, part B: emulators that scan recursively (shadPS4's game directories) may list an extracted update folder under `Updates/` as its own entry; the library layout is the master, device translation fixes it. |
| D6 | `<Game>` and the names | `<Game>` = the base's final stem (after `NameMode`: kept name, or catalogue name, then the safe-name and path-length rules), with the region added by D10 when the stem has none. Children **always** get the canonical names of D5 (whatever `NameMode` says), recorded as a new `RenameReason::GameFolder { from }` so the row says «Se renombra desde …» and undo restores the old name. `<DLC name>`: the DLC's own plaintext title when it differs from the base title (PS3/PS4/Vita `TITLE`, Xbox 360 display name, `cnmt.xml`/`nacp.xml` in clear, GDK `DefaultDisplayName`), else the file stem with the base title and every `(…)`/`[…]` group stripped when anything is left, else `DLC <title id>` (`DLC 0100ABCD12341001`). Two DLC that end on one name get the existing collision suffix ` (2)`. Every header-derived component (`<DLC name>`, the orphan title of D13, the version text) is **untrusted**: it goes through `clean_title` and then the safe-name rule, which removes path separators, `..`, NUL and control characters, so a crafted `TITLE` of `../../x` can never leave the game folder (a test asserts the target stays below `<System>/<Game>/`). Path length: when a child's path exceeds the limit, the `<DLC name>` part is shortened first, then the repeated `<Game>` prefix in the **file** name, never the game folder (so all children keep one folder); still too long → `PathTooLong`. `OrganizeItem.rename` holds one reason: `GameFolder { from }` wins over `Collision`, and the ` (2)` suffix stays visible in the name itself. | Dumpers name children with ids (`0004000E00055D00.cia`, `TU_10DABC.zip`, `[0100…800][v131072]`); the folder layout is only useful if they read as the game. The base keeps the user's naming choice. |
| D7 | Respect the fixed folders: walk | In `organize/walk.rs`, before the console probes: a pile directory whose name is a fixed folder and whose parent holds a game (D3) is handled by role: `Updates/` and `DLC/` are walked as usual, and each item found below gets `role_hint = Update \| Dlc` (used when the header says nothing, D14) and its parent's base as the link candidate; `Mods/`, `Cheats/`, `Extras/`, `Saves/` are **not descended**: one left row each, `LeftReason::GameFolderContent { folder: FixedFolder, of: String }`. A pile directory with fixed folders but no single base at its root is not a game folder (D3): its `Updates/`/`DLC/` items still get the role hint, its `Mods/`-like folders are walked as today (visible rather than hidden). | Brief: never treat files inside the fixed folders as loose games to move out. Mods/Cheats/Extras/Saves move with their game in parts B/D and block 5; leaving them in place is the safe default, and leaving `Saves/` alone can never lose a save. |

## 8. Behaviour in detail

### 8.1 What is a game folder (scan and walk)

Directly under a system folder (scan) or anywhere in a pile (walk), a directory `G` is a game folder when it has **exactly one base at its root**: `G` itself is a folder game a probe already recognises (PS3 JB, Vita, Wii U, PS4/PS5, Xbox), or `G`'s root holds exactly one ROM-like file or one sheet set. Fixed folders alone do not make a game folder (D3). With several root games (a user folder of loose games) or none, `G` is not a game folder: its `Updates/`/`DLC/` files become orphan children (top-level entries with `role`, D8; role hints, D7), and its `Mods/`-like folders are walked and scanned as today. A directory directly under a system folder whose own name is a fixed folder (Batocera `ps4/DLC/`) is never a game's fixed folder. One listing of `G` decides it: the scan reuses the listing `is_console_folder` already takes, the walk its existing `read_dir`; no new pass, no file opened.

### 8.2 Planning order

1. Survey and identify as today; children get `role_hint` from D7.
2. `updates_after_bases` links children to bases by `base_title_id`, now also writing `game.of`; demos link by name (D12); revisions get their group (D15).
3. Targets: bases first, so `<Game>` is known; then children into `folder/Updates|DLC`; then demos; orphans by D13.
4. Licence companions are matched after targets (they need the owner's final folder and the transfer kind).
5. Duplicates step as today, with role-aware keys.

### 8.3 Undo

The journal already records `DirCreated` and each `Moved`. Undo walks the journal backwards: children go back first, then the base, then empty `DLC/`, `Updates/`, `<Game>/` are removed (never a folder that holds anything else, for example a `Saves/` a user added after the run). A licence companion goes back like any companion.

Review against generic defaults: the default would be a file-manager tree with folder and file icons on every line, chevrons per level, and a coloured «DLC» pill on each child. Rejected: icon-per-line trees read as a file browser and double the row height; pills turn a fact into a badge wall. The single spine and indentation say «inside» with one device, and the counts in parentheses carry the information a pill would. A second default, a full-width destination tree panel beside the list, was rejected for part A: it competes with the rows for width at 390 px and belongs to part C's Columns view.

Accessibility: the preview is a `ul` nested per level (real list semantics, `aria-label` «Carpeta de Pokemon Y (World)»), the disclosure is a button with `aria-expanded`; the version is text («versión 1.1.0»), never colour; the switch is the existing labelled switch with its hint as description; keyboard order: row checkbox, name, disclosure, child rows. The disclosure button keeps focus when it closes; its hit area is at least 24 × 24 px (WCAG 2.2 target size) at 390 px; the tree's indentation is real list nesting, so it reads the same with styles off, in forced-colours mode (the spine uses `border`, which forced colours keeps) and at 200 % zoom (names wrap, paths break at separators with `overflow-wrap:anywhere` in mono). The «remembered per session» state lives in `sessionStorage` under the base's source path, every access in `try/catch`, and the page renders collapsed when storage throws.

## 11. Data flow

```
pile ─walk─▶ candidates (+ role_hint from Updates/ DLC/; Mods/Cheats/Extras/Saves → left)
     ─identify─▶ ConsoleId { kind, version, region } (plaintext only; licences never opened)
     ─plan─▶ link (base_title_id → game.of; demos by name) ─targets─▶ <System>/<Game>/[Updates|DLC]/…
     ─licences─▶ Companion { licence } (move + same volume + one owner) else left
     ─dedupe step (roles)─▶ OrganizePlan ─IPC─▶ Organizar (folded rows, preview)
apply ─journal─▶ DirCreated <Game>/, Updates/, DLC/; Moved base, children, licences ─undo─▶ reverse
library ─scan─▶ RomEntry { children, role, version_group, revision } ─▶ fill/gamelist/audit (top-level only), dedupe (units with roles)
```

## 12. Edge cases and failure modes

| Case | Behaviour |
|---|---|
| Update and base in the pile, base left (unreadable, too big for FAT) | The update follows its base's action (existing sibling rule): left too, with the same reason, so a game folder never holds an update without its base by surprise. |
| Two bases with one title in one system (different title ids) | Two folders; the second gets the collision name `(2)`; region in the name usually separates them first (D10). Children fold by `game.of`, so each stays with its own base. |
| Base already in the library flat (`3DS/Pokemon Y.cia`), update in the pile | The library facts (D13) find the flat base by `base_title_id`: the update goes flat beside it, Auto as today, with no `BaseMissing` and no folder created around a file the user did not pick (D19). |
| `Updates/` in a pile folder holding several games | Not a game folder (§8.1): its files are planned on their own headers (orphans if the base is not found), and `Mods/`-like folders are still left. |
| A user `Extras/` holding a 3DS soundtrack `.cia` | Never descended in the pile, never scanned in the library, never a dedupe unit. |
| Case-different fixed folder on disk (`updates/`) | Matched (D3); Organizar reuses it with its casing instead of creating `Updates/` beside it (on case-sensitive volumes too). |
| `Updates` exists as a file inside `<Game>/` | Fixed names never get ` (2)`: the child stays in place with `LeftReason::UnsafeTarget`. |
| Path too long on Windows | `PathTooLong` per item as today, counted over the deeper path; the base may move while a long-named DLC stays: the DLC row says why. |
| FAT32 target and a 4 GiB+ update | `TooBigForFat` as today. |
| Copy mode | Children and bases copy into the game folder; licences stay (copying reads them, D17) with the key-material reason. |
| Volume unplugged mid-apply | Existing pause/resume: the journal knows which children moved; resume continues, undo reverses what moved. |
| Licence matches two items (`.rap` beside a base and its DLC with the same content id) | Ambiguous → left. |
| `keys.txt` that is a readme | Left with the key-material reason; never opened (cost accepted, D17). |
| Header says Base, file sits in a pile `Updates/` | Header wins (D14): planned as a base. |
| Unknown kind in `DLC/` with no base anywhere | Orphan DLC by role hint, Review, `BaseMissing`. |
| Revision `(Rev 1)` and untagged in Duplicados with «una ROM por juego» off | Reported as versions; no action. On: the keeper is `(Rev 1)` when the rules before `Revision` tie (a save or play count on the untagged copy keeps that one instead, by the user's rule order, D15), the other goes to quarantine/Trash per settings; the guard refuses to act if the plan would remove both. |
| Switch DataPatch without its DLC | Linked to the base by `switch_base`, filed under `DLC/` with its own id as the name fallback. |
| Xbox One: two XVDs with one ProductId | Versions of one game (no update role); Duplicados suggests the higher `PackageVersion`. On disk each is a base: the second gets the collision folder `<Game> (2)/`, Review. |
| Undo after the user added a save to `<Game>/Saves/` | `<Game>/` is not empty: undo moves the files back and leaves the folder, reporting it as kept (existing «carpeta no vacía» outcome). |
| Option toggled between plan and apply | The plan stores its targets; apply follows the plan. |
| Duplicados picks another copy as keeper of a base whose folder holds `Updates/`, `DLC/` or `Saves/` | That base is not removed; the group is reported with «Tiene actualizaciones o DLC en su carpeta: no se quita» (D9). |
| A user folder `SNES/Hacks/` holding `Mods/` and many ROMs | Not a game folder (no single base, D3): scanned and walked as today, nothing hidden. |
| Batocera library with `ps4/DLC/CUSA00001/` | A fixed folder directly under a system folder is not a game's (D3): unchanged. |
| Library detected as MinUI because of `.media/` (Coverly library, «Automático») | Scan still respects game folders (D1); art template is the same; Ajustes → Biblioteca can pin «Coverly». |
| Volume changed between plan and apply, licence rename gets `EXDEV` | The licence stays in place with its row; the base's move stands; never a copy (D17). |
| Header title `../../evil` as a DLC name | Safe-name strips separators and `..`; the target stays inside `<System>/<Game>/DLC/` (D6, tested). |
| Linux volume with both `DLC/` and `dlc/` in one game folder | Both read as DLC; Organizar fills the one sorting first, never creates a third (D3). |
| User downgrades to a build without game folders | Settings keep loading (the `game_folders` map is ignored); `default_layout = coverly-library` fails validation there and falls back to that build's default, as any unknown id does; the journals use only existing ops, so undo from the older build works; the older scan counts updates in `Updates/` as games again (expected, nothing moves). |
| A custom profile file `coverly-library.toml` from before | Kept as `coverly-library-custom`, settings references follow, one warning (D2). |
